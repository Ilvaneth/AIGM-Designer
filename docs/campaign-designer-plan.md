# Campaign Designer — Master Plan

*Planning document only. Started 2026-09-24 in a development tab. Nothing under `.claude/skills/dnd/` is written until this plan is agreed item by item. Each item below is discussed in order; its **Decisions** block is filled as we go and its status moves `open → discussed → decided`. Conversation is in Turkish; this file is in English (development artifact).*

## Goal

Replace the thin `/dm:dnd new` with a **Campaign Designer** that builds a full, unique campaign bible before session 1 (premise, cosmology, history, geography, settlements, factions, guilds, gods, planes, antagonists, NPCs, dungeons, arc) which the DM then reveals progressively at the table. The designer is three things: a **birth** pipeline, a **just-in-time elaborator** during play, and a **revision** tool when players go sideways.

## Standing principles (agreed so far)

- `/dm:dnd new` **is** the designer; the old flow is retired, not kept as a default.
- Phase-by-phase approval with a correction round after each phase.
- Scale is chosen by the player: `short` / `standard` / `epic`; all counts derive from it.
- A visual map is generated.
- **The world does not scale.** Every site carries a fixed danger tier set by the fiction. A level-3 party in a CR 15 site runs or dies; the designer owes legibility (telegraphs) and escape geometry, never softening.
- Data-first: one entity registry (canonical at `design/dm-only/entities.json`, with `design/entities.json` as its generated public+discoverable projection), prose derived from it, a validator that checks every reference (errata 24.2 #1).
- Immutable = stamped fields; play-time truth lives in the overlay (`design/overlay.json`), never in a rewritten bible (errata 24.2 #2).
- Design depth decays with distance from session 1; later content is skeleton until JIT elaboration.
- SRD 5.1 YAML (`data/srd-5.1-yaml/`) is a design input: monsters, NPC stat blocks, magic items, gods (as domain scaffolding), planes (as a baseline to deviate from), traps/diseases/poisons/madness, backgrounds, equipment and prices.
- Reference for the target output shape: `campaigns/ashen-crown/reference/` as it stood at session 26+ (outline, dungeon directory, consequence calculus, geography, quest seeds, travel tables, master index) plus `factions.json`, `goals.json`, `graph.json`.

## Items

### 1. Scope & command surface
**Question:** what commands exist, what each takes and produces, and what happens to `/dm:dnd import`.
**Decisions (2026-09-24, decided):**
- Commands live under a `design` namespace; `new` is the one exception and stays top-level.
  - `/dm:dnd new <name>` — the birth pipeline, phase by phase with approval/correction after each phase. Output: `campaigns/<name>/` hot-path files + `design/` bible.
  - `/dm:dnd design status` — manifest: phases done, each site's state (skeleton / detailed / played), last validator result.
  - `/dm:dnd design phase <n>` — rerun one phase after a correction; later phases are marked stale.
  - `/dm:dnd design detail <id>` — JIT elaboration of a site / settlement / faction / NPC to full depth under the bible's constraints.
  - `/dm:dnd design check` — the validator.
  - `/dm:dnd design integrate` — character integration pass, run after `character new`.
  - `/dm:dnd design primer` — regenerate the player primer.
  - `/dm:dnd design revise "<change>"` — **player-only** override of the bible (e.g. "swap this god"). The DM never invokes it. `revise` means a change of canon only; the play-time act of picking one of a beat's designed fallbacks is a separate command, **`arc fallback`** (item 10.3), which the DM may call (errata 24.2 #7).
  - `/dm:dnd design ask "<yes/no question>"` — the blind proxy over dm-only content: a fresh agent answers only `evet / hayır / spoiler vermeden cevaplanamaz`, logged in `design.json` (item 14.4; 24.6 #6).
- Lifecycle: `new` → `character new` (×party) → `design integrate` → `load` → during play the DM calls `detail` as needed; `check` runs at every `save`.
- **`detail` is triggered by the DM itself**, when the party is *approaching* a skeleton site (before the scene opens, never once they are inside). The player may also call it by hand. `detail` **adds** depth; it never alters a stamped fact (danger tier, thread, key NPCs) — the validator enforces this.
- **The bible is immutable during play.** Bible = design-time canon; `state.md` / `factions.json` / `goals.json` = play-time truth. "Immutable" means the **stamped fields** (item 3); play-mutable state of designed entities (control, ruler, alive/dead/fled, current location, site/settlement status, `seen_in_play`, price modifiers with `until_day`, threat stage) lives in the script-owned `design/overlay.json`, written only by `simulate`, `site_progress.py`, `campaign_graph.py`, `factions.py` and `registry.py play-set` (errata 24.2 #2). When players deviate (a lieutenant killed early, a town burned) the event is recorded in state, the bible is not rewritten, and the DM plays around it. Consequence-shaped beats (item 10) are what let the arc absorb deviations without edits.
- Out of scope, deliberately: character creation (`character new` stays), play flow (`load` / DM mode unchanged), dice/combat/calendar tools (unchanged; the designer calls them).
- `import` is not touched now. Long-term target: import feeds the same entity registry so `detail` / `check` work on imported campaigns too — a separate follow-up, noted under item 21.

### 2. Dials (Phase 0) and the scale table
**Question:** the full dial list (tone, magic, era, danger, level range, party size, target session count, language, player wishes, seed), and the concrete numbers per scale (regions, settlements, factions, NPCs, sites, chapters).
**Decisions (2026-09-24, decided):**

Phase 0 is the designer's only questioning moment. Every later value derives from these dials and from dice.

| Dial | Values | Note |
|---|---|---|
| Ruleset | 2014 / 2024 | exists |
| Scale | short / standard / epic | new; drives every count below |
| Tone | grimdark / dark fantasy / heroic / horror / political / swashbuckling / cosmic | exists |
| Magic level | low / medium / high (never none, errata 24.2 #24) | exists |
| Era / setting | medieval / renaissance / ancient / nautical / underground | exists |
| Danger | lethal / gritty / standard / heroic | exists; aligned with state.md `difficulty`; touches only non-CR knobs — number and proximity of over-tier Act 1 sites, rest pressure, telegraph explicitness, rumour visibility, the reference party's step-up for a 1-2 PC table — never a site's tier (errata 24.2 #8) |
| Party size | 1-6 | exists |
| Starting level | default 1, player may change | new (dial); the level band is `start .. start + span`, span 4 / 11 / 19 by scale (errata 24.2 #8) |
| Content mix | ordered top three of exploration / politics / war / horror / mystery | new; sets the site-vs-social ratio and site types per chapter, so a "three sessions of politics in a row" imbalance is prevented at design time |
| Narration language | tr / en | exists |
| Player wishes | 1-3 "must have", 1-3 "must not" (free text) | new; hard constraints carried into the premise and every phase |
| Seed | auto-generated, shown, reproducible | new |

- Any dial left blank is rolled with `dice.py` and logged (`d6=4 → political`). **The player sees the rolls live** in Phase 0; the roll log is also kept in `design.json`.
- `spotlight` / `pacing` are table dials, not world dials: not asked in Phase 0, still offered at `load`.

Scale table (agreed numbers):

|---|---|---|---|
| Level range | 1-5 | 1-12 | 1-20 |
| Target sessions | 8-12 | 20-30 | 40-60 |
| Acts / chapters | 1 act, 3 chapters | 3 acts, 6-8 chapters | 3 acts, 9-12 chapters |
| Polities | 1 | 2-3 | 3-5 |

Ashen Crown's Chapter 2 alone has 31 sites, i.e. above `epic`; the table is deliberately not pushed that far because skeleton count at birth grows the unread part of the bible. Epic grows during play through JIT elaboration.

The Named-NPC row was re-derived from the role quota (faction leaders + heirs, rulers, anchor owners, antagonists, sockets, free radicals) under item 8.1's stacking rules, with P9 headroom (+1 NPC, +1 site per PC per act) included; the earlier 10-12 / 20-30 / 40-50 figures were over-subscribed by the quota (errata 24.2 #3; 24.6 #4). The Level-range row assumes a starting level of 1; the general form is `start .. start + span` with span 4 / 11 / 19 by scale (errata 24.2 #8).

### 3. Entity registry (data-first architecture)
**Question:** schema of `entities.json` (ids, types, fields per type, cross-references), how prose files reference ids, what the validator checks.
**Decisions (2026-09-24, decided):**
- **File:** the canonical registry is `campaigns/<name>/design/dm-only/entities.json` — the single catalogue of everything that exists in the campaign; `design/entities.json` is the generated public+discoverable projection of it, regenerated on every `registry.py merge`, and is the only form the conductor and `campaign_search` see (errata 24.2 #1; 24.6 #1). Prose files reference it; `graph.json`, `factions.json`, `goals.json` and `name_registry` use its ids. (Today Ashen Crown carries the same faction under two ids, `faction_concordat` in the graph and `ashlord-concordat` on the board; the registry exists to end that.)
- **Id scheme:** `<type>_<slug>`, matching graph.json's existing convention. Types: `god_`, `plane_`, `era_`, `event_`, `polity_`, `region_`, `settlement_`, `district_`, `faction_`, `npc_`, `site_`, `item_`, `creature_` (custom / reskinned), `chapter_`, `node_`, `seed_`, `thread_`, `socket_`, plus `place_` (a settlement small point: settlement, district, kind, owner, services) and `pc_` (a player character, the owner of a thread) (errata 24.2 #14). Rooms are **not** entities; they live in the site file as a table. A notable item or creature inside a room *is* an entity.
- **Registry holds the queryable subset, not the whole entity.** Common fields: `id`, `type`, `name`, `aliases`, `summary` (one line), `file` (prose file), `secrecy` (public / discoverable / secret — the three-truths tiers, mandatory on every entity), `created_phase`, `status` (sites and settlements only: skeleton / detailed / played), `stamped` (immutable facts), `refs`. Type-specific fields stay short: site → `danger_tier` (stamped), `thread`, `region`, `telegraphs[3]`, `escape`, `attitude_to_intruders`, `xp_budget`, `room_count`; npc → `faction`, `location`, `role`, `alignment`, `goal_tracked`, `tier` (major / supporting / minor — the one field `detail` may raise, when a minor NPC is promoted) (errata 24.2 #14); faction → `archetype`, `power`, `hq`; god → `domains`, `alignment`, `church`; settlement → `scale`, `population`, `ruler`, `polity`. Of these, `status`, `seen_in_play`, an npc's current `location` and a settlement's current `ruler` are **overlay fields** (`design/overlay.json`), not registry fields: the registry keeps the birth value, the overlay the play-time one (errata 24.2 #2). The rich narrative lives in the prose file.
- **Registry vs graph:** the registry says *what exists and what it is*; the graph says *who relates to whom, since when*. Same ids. Graph nodes are seeded from the registry at birth; edges live only in the graph.
- **`stamped`:** per entity, a set of fields frozen at birth (site: danger tier, thread, key NPCs; npc: secret, faction; faction: objective). `detail` may add anything else but never changes these; the validator diffs them against the birth snapshot. This is the mechanical form of "the bible is immutable" (item 1).
- **Prose references ids inline** with wiki-links, `[[npc_thessaly_ondrel]]`, plus a front-matter `entity:` line naming the file's own entity. Players never see them; the DM translates id → name when narrating. Benefits: the validator resolves every link, reverse lookup ("where does Oskar appear?") is a grep, and a rename touches the registry and regenerates the files the link scan lists (errata 24.2 #16).
- **Validator checks through the registry:** every `[[id]]` resolves; every entity's `file` exists and its front-matter matches; stamped fields equal the snapshot; every site has thread + 3 telegraphs + escape + attitude; every faction has an operation on the board; every `goal_tracked` npc has a goals.json record; ids unique across registry + name_registry; counts within the scale band; no danger tier anywhere derived from party level.

### 4. Premise engine (uniqueness)
**Question:** theme-as-question, the big secret, three signature elements, trope-break table, forbidden-defaults list, per-culture naming languages, optional signature mechanic.
**Decisions (2026-09-24, decided):**

The premise phase runs first, before cosmology; everything downstream derives from it. Output: `design/premise.md` (player-safe part), `design/dm-only/premise-secret.md`, registry entries, `design/naming.json`. Its job is to break regression to the mean structurally, with specific, committed choices rather than randomness.

1. **Theme is a question.** Tone is an adjective; theme is the one question the campaign tries to answer ("what happens to the one who finishes the power?"). Rolled from a *thematic tension* table (~30 rows: legacy/freedom, order/mercy, knowledge/sanity, faith/proof, power/self, memory/salvation...), 1-2 rows; the LLM writes the question. **The villain embodies one answer, the world's default the other; the finale turns on the party's answer.** Resolution and beats derive from it.
2. **The big secret.** One DM-only truth about the world's nature, from an archetype table ("the gods are actually X", "magic is actually Y", "history lies in way Z", "the artifact is a seal", "the villain is right", "the world is ending and everyone suppresses it", "the enemy is us"). Mandatory three-clue trail (Act 1 surface / Act 2 investigation / Act 3 deep), clues placed in sites, validator-checked. Ashen Crown's "the Crown is a seal on the erased seventh god" is the model.
3. **Three signatures**, unique to this campaign: a **magic phenomenon** (a unique rule), a **culture or creature** (a people/species of this world, SRD reskin allowed), an **institution** (guild, court, rite). Each must appear in ≥3 other entities (validator counts).
4. **Trope break.** A ~40-row table ("the undead are the civilised ones", "dragons are extinct and their bones are currency", "there is no afterlife and everyone knows it", "no kingdoms, only city-states and one road", "the gods are the souls of mortal ancestors"). Count by scale: short 1, standard 2, epic 2. Mandatory and pervasive.
5. **Forbidden defaults**, fixed in the prompt: awakening ancient evil, chosen one, prophecy, dark lord in a black tower, generic evil cult, corrupt church as default villain, amnesiac hero, tavern opening, a monolithic "Empire", inherently evil races. Any of these may return only as a *conscious* trope break, never as a default.
6. **Naming languages.** Per major culture (polity / people) a seeded sound system: syllable bank, onset/nucleus/coda sets, length, forbidden clusters; 2-3 languages per campaign, stored in `design/naming.json`. God, place and person names are generated from their culture's language, then checked by `name_registry` across campaigns.
7. **Signature mechanic — rolled.** A campaign-specific rule system (corruption track, reputation ledger, a relic set with thresholds; Ascension tracks are the model). Roll: short never, standard 50%, epic always. Template: track + thresholds + gains + costs, wired to a `goals.py`-style tracker.
8. **Two pitches.** A spoiler-free player pitch (3 sentences: the question, the signatures, the trope breaks — what the player will *experience* as different) and a DM pitch (secret included).

**Critique pass question for this phase:** "Could this premise describe a hundred other campaigns? Show the three sentences that could only be true here." If it cannot, the phase reruns.

**Approval is two-layered, and the owner stays a player.** The user is both player and owner and does not want to know DM-only content. In the premise phase they see and approve only the player pitch, the signatures and the trope breaks. The big secret and the DM pitch go to `design/dm-only/`, which the user does not open. The same rule holds for every later phase: structure (counts, names, map, faction list) is approved; anything with `secrecy: secret` is never put in front of the user. This shapes the approval loop in item 19.

### 5. Cosmology, pantheon, planes, magic, history, calendar
**Question:** pantheon generation on the SRD domain scaffold, plane deviations from the SRD baseline, magic system, timeline (ages + dated events), calendar init.
**Decisions (2026-09-24, decided):**

First generation phase after the premise; everything here serves it (the big secret usually hides in this layer, the trope breaks usually take concrete form here).

- **Pantheon.** Count by scale (3-5 / 6-9 / 9-14). Pantheon type rolled (polytheist / dualist / dead gods / silent gods / ancestor-gods), overridable by a trope break. Each deity is a `god_` entity with a **`rank`** field (`greater` / `lesser` / `power`) — saints, archfey, demon lords and primordials are the same entity class, one table, one naming language, one relationship web. Fields: name (from its culture's naming language), **domains from the SRD cleric domain list** (Knowledge, Life, Light, Nature, Tempest, Trickery, War, Death) so clerics and paladins work mechanically, alignment, symbol, disposition to mortals, **church/cult** (where strong, which faction, as an institution — the `church` field is filled for every god at every scale, but separate `faction_` church entities per god are created only in `epic`; in `short`/`standard` the field points at item 7.2's religious faction or a named institution) (errata 24.2 #11), inter-deity relationships (rivalry, alliance, the silenced one), a secret with a secrecy tier. The SRD's four historical pantheons are used only as a *structural scaffold* (how domain/symbol/alignment rows are built); no names or personalities are taken. What common folk believe (`public`) goes to the primer; what is true (`secret`) to dm-only.
- **Planes.** Baseline is the SRD cosmology. The designer decides which planes exist unchanged, which are renamed/altered/removed by a trope break, and which are **touched** (0-1 / 1-2 / 3+ by scale). A touched plane has a way in, a cost, a site and a time rate (`calendar.py plane enter --rate`). Untouched planes still exist for spells (Banishment, Plane Shift); rule: plane-referencing spells work according to this world's cosmology, stated in the primer.
- **Magic system.** Availability from the dial; source, constraints, visibility, taboos, **who regulates it** (an institution, often the signature institution itself); the signature magic phenomenon is defined here. Wild magic yes/no rolled.
- **History.** 3-5 named ages; 8-12 dated events in the last 200 years (500 in epic) plus **3-5 deep-past events** (enough: Ashen Crown's "the Crown was broken four centuries ago" spine is this kind of event). Each event is an `event_` entity with two layers: **as taught** (public) and **as it happened** (discoverable/secret). The villain's origin and the big secret are pinned to the timeline. **Living memory:** which NPCs witnessed which events — the seed of the Known Facts ledgers (item 8).
- **Calendar.** Always custom: month names from the naming language, day names, seasons with a **per-month sensory tone** (temperature, sky, smell — for the "felt season" rule), moon(s) and phases, festivals derived from the gods, a start date anchored to the timeline. **Months are always 30 days** (Ashen Crown's 45-day months did not play well). `calendar.py init` is called directly.

**Critique pass question:** "How does this pantheon and cosmology carry the premise's question — which god embodies the villain's answer, which the world's?" No answer means the pantheon is scenery; the phase reruns.

### 6. Geography, settlements, travel, the map
**Question:** polities/regions/settlements by scale, the settlement template, travel-times and per-region encounter tables (danger by region, not by party), SVG map generation.
**Decisions (2026-09-24, decided):**

Three Ashen Crown lessons shape this: hand-chained travel times produced a live error (session 24); pre-generating every small point of a 120k city was rejected for staleness; city interiors never needed a travel table, only the road *to* the city did.

1. **The map is a graph; the picture derives from it.** `design/map.json`: nodes (settlement / site / landmark / waypoint) with coordinates, region, terrain; edges (routes) with days on horseback, terrain, road quality, region. `travel-times.md` is **generated** from shortest paths, never written by hand, so the "a place reached via a hub can never be closer than the hub" rule is automatic. The SVG map is rendered from the same file (existing parchment style kept), with city insets. **Two versions:** the player map shows only `public` nodes; the DM map shows all. **Coordinates: the LLM proposes** (100×100 grid, region constraints), **the script validates** (a 2-day route may not draw longer than a 5-day one) and renders.
2. **Regions.** Count by scale. Each: name, biome/climate (dial + dice), **fixed danger tier**, a one-line tonal identity distinct from every other region (no reskins), polity, factions present, 2-4 landmarks, and a travel table in the Ashen Crown format (six categories, `[KANCA]` hook marks). Regions unreachable by normal travel (Grey Kingdom type) exist off-graph as an inset.
3. **Polities are factions with archetype `state`.** Government, ruler (npc), capital, law level, economy and stances toward other polities live in `factions.json`, not in prose.
4. **Settlement template.** Scale (village / town / city / metropolis), population, wealth, law 1-5, polity, ruler, three truths, districts (city 5-8, town 2-3, village none), **anchor locations fixed at birth** (temple, guild hall, inn, market, seat of rule, one signature place), a **small-point budget** (city 30-40) filled JIT, each filled small point a `place_` entity (settlement, district, kind, owner, services) (errata 24.2 #14), economy (sells / needs / price modifier), what the settlement fears, one local problem (a quest seed), NPCs assigned from the roster. Villages are light: one sentence, one problem, one NPC.
5. **Travel.** Mounted by default. Region tables generated at birth. **The Early/Late tier is keyed to the threat escalation stage, not to party level**: roads get more dangerous as the world darkens, not as the party levels. This is a skill change (`SKILL-travel.md`, `travel.py --tier`), noted under item 21.
6. **Map rendering** is a script, `map.json → SVG`.

**Critique pass question:** "Are these regions distinct only by name? For each region, show one travel result that could happen only there."

### 7. Powers: factions, guilds, antagonist hierarchy, fronts, the living world
**Question:** faction archetypes and counts, guild system, BBEG + lieutenants + regional villains, countdown clocks tied to calendar days, seeding `factions.py` / `goals.py`, consequence calculus.
**Decisions (2026-09-24, decided):**

Two Ashen Crown lessons: factions started as monoliths and each later needed an internal fracture; Chapter 2's B scenario was first built on Chapter 1's actors and had to be redone — each act's danger must grow from that act's own ecosystem. `factions.py` and `goals.py` already take every field a faction needs; the designer calls them, it does not invent a parallel format.

1. **Faction dossier standard:** Ashen Crown's four-phase format, adopted as is: *Identity & Belief* (public position, true belief vs cover, founding, alignment range, relation to the gods) / *Power & Resources* (military, magical, economic, territory, reach, signature presentation, typical forces anchored to an SRD NPC stat block) / *Structure & People* (hierarchy, key-NPC web, **internal fracture**, betrayal candidate, relations with every other faction, recruitment and exit terms) / *Intelligence & Operations* (network, decision logic, **endgame**, vulnerabilities, default policy toward the party). Each faction = `design/factions/<id>.md` + registry entry + `factions.json` row.
2. **Count and archetype quota, by scale** (3-4 / 6-10 / 12-16): at least one `state` (the polities, item 6), one religious (a church from the pantheon), one guild, one criminal/secret society; the premise's signature institution is one of them. In `short` the quota fills the count (religious optional); in `standard`/`epic` the rest are rolled from martial, scholarly, resistance, cult, trade consortium.
3. **Guilds** are factions with archetype `guild`: mage guild (the regulator from item 5), thieves/undertow, merchant consortium, craft guilds. Each: membership terms, **services to the party** (training, identify, fencing, information), dues, a fracture. Every faction leader gets an **access chain** (who must be satisfied before whom) per Standard 10.
4. **Mandatory per faction (validator counts):** fracture, secret, endgame, betrayal candidate, a stance toward every other faction (-3..+3 → `factions.json`), power 1-5 and intel 0-3, assets, an HQ that exists, a reaction doctrine per trigger (alliance / loss / gain / exposure / death / betrayal), a **first operation** with dated steps + abandon-if + optional countable metric. The board is full on day 0.
5. **Antagonist hierarchy.** The BBEG embodies the villain's answer to the theme question; lieutenants and regional villains by scale. Each antagonist is an `npc_` with a faction and a **front** (the BBEG and lieutenants additionally a goal-tracker record, `goals.py add` with threatened / blocked / permanent-loss pre-written): 4-6 grim portents on calendar days (as `factions.json` operation steps) and a **doom** if never stopped (= threat escalation stage 5). Lieutenants run shorter clocks; regional villains are site bosses at fixed CR. Of the antagonists, only the BBEG and the lieutenants are major tier with a `goals.py` record; **regional villains are supporting tier** — a full dossier, no goal-tracker record, and their front lives on their faction's operation rather than on a record of their own (errata 24.2 #3; 24.6 #4). **The BBEG's doom sits on a hard calendar** derived from the target session count (standard: ~25 sessions × ~5 in-world days ≈ 125 days ± slack) with abandon-if conditions; the party can be too late, consistent with "the world does not scale". **BBEG visibility is rolled per campaign** from a pattern table so it is never the same twice: known and untouchable / known but the wrong person / behind a visible front / a mystery among several candidates / not a person but a process or institution.
6. **Consequence calculus:** a provocation ladder per major actor at birth (3-4 rungs, the first never "war"), `design/consequence-calculus.md`, plus an A/B scenario per act drawn from that act's own ecosystem.

**7. The living world — faction simulation.** The user's requirement: the world must move and live; factions play their own chess independent of the party. Today's `factions.py` is a good ledger but nearly every move is a reaction to a party event and outcomes are resolved in the DM's head. The extension:

- **`simulate --from-day A --to-day B`.** Each week, each active faction in turn: (1) picks a target from its objective, stances and doctrine (the party is just one actor on the board; most weeks the target is someone else); (2) spends move points on a move from a bounded list (seize / sabotage / bribe-ally / spy / persuade-propaganda / assassinate / besiege / negotiate); (3) **resolved with dice** via `dice.py`, an opposed check (attacker power+intel+points spent vs defender power+intel+asset defence) — the DM never picks the outcome, Standard 7 holds here too; (4) the result is written to the world: an asset changes hands or is destroyed, a stance shifts (betrayal −2, alliance +1, decaying toward baseline over time), an operation step advances or fails, an NPC dies; (5) every resolved move emits a **news record** (`news.json`: region, settlement, visibility public/rumored/secret, day, one line of "what the party would see", and `refs[]` — the registry ids the record touches, so item 13.1(c) can match a record to a site) (errata 24.2 #16); (6) **cascade**: a resolved move is an event, `react` runs automatically, other factions learn with intel delay and answer next turn, chain length capped per tick.
- **Four building blocks it needs:** assets are map things (registry entities: control of a settlement / site / NPC), so a move can only take or break something that exists and control changes flip region tables and settlement rulers; a **succession rule** (every leader has a pre-written heir; an organisation never goes leaderless, doctrine shifts slightly on succession — Ashen Crown's Whisper Court fell into exactly this gap after Iskra); **fronts drive the threat escalation table** (stages 1→5 advance on BBEG front steps, not on DM feel); a **light economy** (settlement price modifiers move with faction control and events: war → weapons up, siege → no food).
- **Coupling to play:** `simulate` runs at `load` for elapsed days (replacing today's `tick`), at `end` alongside `sweep`, and mid-session whenever the calendar jumps 7+ days. When opening a scene the DM pulls news records for the party's current region; the travel table's Faction/Political and Discovery results consult the news feed before falling back to generic lines (SKILL-travel rules 1 and 5 finally get data).
- **The designer seeds:** per faction a target-priority list, doctrine, on-map assets, heir, first operation; for the BBEG the hard-calendar front. Then the world turns on its own.
- **Two brakes:** when a move targets an asset that matters to the party (an allied NPC, the party's own holding) the move is parked as a `pending_scene` for the DM ("this belongs in a scene") and the simulation continues — charter rule 3 below (24.6 #3) (the same threshold rule as the dead-time skip); and each week's resolutions are shown to the user as a summary at `end`, secret items excluded.

- **Simulation charter — five rules (24.6 #3):** (1) **Load-bearing armour is on:** a `load_bearing` set is computed at every `simulate` (key NPCs of unplayed sites, delivery paths of unresolved beats, clue holders, thread layers and antagonists, unfilled sockets, unresolved hooks); removing outcomes against it cap at threatened / wounded / fled and are parked; the BBEG and lieutenants never die off-screen; regional villains fall only to a tier-matched faction, as a parked scene. (2) **The doom day is fixed at birth;** it moves only later and only through a party-caused structured block; a failed contested step retries at cost. (3) **Brake = park**, never halt: a move that touches a party asset becomes a `pending_scene`; `load` prints pending scenes first; the dead-time skip stops on the first pending day. (4) **`controller: party` factions are never auto-moved.** (5) **The engine is deterministic** — seeded in-process rng, machine doctrine fields (`aggression 0-3`, target preference, per-trigger move weights, structured `abandon_if` predicates on the overlay), the LLM only rendering news into the narration language — under a weekly volatility budget in `scale.yaml` (≤1 control flip, ≤2 large stance shifts).

**Critique pass question:** "What does this faction want independent of the party, and what would it have done 60 days from now if the party never appeared?" If the answer is "it waits", the faction is scenery.

### 8. People: the NPC roster and dossier standard
**Question:** roster size by scale, the full-entry rubric, graph seeding, Known Facts baseline, name registry, schedules.
**Decisions (2026-09-24, decided):**

Ashen Crown's mature NPC format (the Sereth Corr entry) is richer than the template: concrete appearance, dated motivation, *how* the secret surfaces, a weakness that follows from personality, goal tracker, Known Facts. SKILL.md Standard 5 already says an NPC is finished in one pass; the designer enforces it at birth.

1. **Roster size and role quota.** By scale (14-18 / 30-40 / 60-80, re-derived from the role quota with P9 headroom of +1 NPC and +1 site per PC per act) (errata 24.2 #3; 24.6 #4). The roster fills from roles, not at random: faction leaders + heirs (item 7), settlement rulers and anchor-location owners (item 6), antagonists, **ordinary people** (innkeeper, smith, priest — the party's daily contacts), hook-socket NPCs (candidates for PC backstories), and 2-3 **free radicals** (unaffiliated wildcards). **Stacking rules** (`scale.yaml` / `npcs.yaml`) keep the quota inside the cap: at most 2 roles per person; a polity's ruler is its faction leader; a lieutenant is a faction leader; heir, betrayal candidate and anchor-location owner default to minor tier or a registry stub; socket NPCs are drawn from the roster, not added to it; sockets are party×2 in `short`. The validator counts roles per person and roles left unfilled (24.6 #4).
2. **Three depth tiers.** *Major* (full dossier + goal tracker + Known Facts ledger), *supporting* (full dossier, no tracker), *minor* (index row + three lines: one physical detail, what they want, a speech tic). Counts: short 3/4/4, standard 6/10/12, epic 10/18/20. These tier counts predate the re-derived caps; `scale.yaml` rescales them to the 14-18 / 30-40 / 60-80 bands of 8.1, with, of the antagonists, only the BBEG and the lieutenants in the major tier (regional villains are supporting tier, dossier without tracker) (errata 24.2 #3; 24.6 #4). When a player latches onto a minor NPC, JIT promotes them to a full dossier (Standard 5).
3. **Dossier standard (major/supporting):** the Ashen Crown format — appearance (species included, concrete), role/CR/location, alignment, demeanor, **motivation with history**, secret + **surfacing path** + secrecy tier, weakness derived from personality, attitude to party, faction, current goal, schedule, four personality axes, ≥2 relationships (knows / owes / hates / fears / allied), speech quirk, goal tracker (major), Known Facts — plus four additions: `heir` / `heir_of` (succession, item 7); **voice samples**, 2-3 sentences in the NPC's own voice so every NPC has a distinct way of speaking and the voice stays consistent across sessions; **what they can offer the party / want from the party** (service, information, work); **what changes if they die** (short: who succeeds, which thread breaks). **Stat anchor:** every NPC is tied to an SRD stat block (NPC appendix or monster), class NPCs get a level; every combat-capable NPC has a fixed CR.
4. **Species and gender are deliberate.** A demographic table per culture (which species, in what proportion); NPCs rolled from it. The validator flags drift when **more than 65% of the roster is one species or more than 65% one gender**. This is the mechanical form of Standard 5's "a roster drifting to human men is an oversight".
5. **The relationship web is seeded into the graph:** every NPC `add-node` from the registry, every relationship `add-edge --since 0`. Validator: every NPC ≥2 edges, no isolated islands, every NPC within 2 hops of a faction or settlement.
6. **Known Facts baselines are filled at birth** from item 5's living memory (who witnessed which event) plus what the role implies. The designer also pre-registers **standing private channels** (`channels.py add`: a faction's internal correspondence, the court's council chamber) so the source-of-knowledge check works from day one.
7. **Names** come from the culture's naming language; `name_registry check` + `add` at birth; no first-name collision inside a campaign (validator).

**Critique pass questions:** "What does this NPC want that has nothing to do with the party?" and "Show the one contradiction that makes them a person."

### 9. Sites & dungeons
**Question:** fixed CR bands, site directory, three-distance telegraphs, escape geometry, attitude to intruders, ecology from SRD + `monster-ecology.yaml`, XP budget for the intended path, room-count derivation, loot budget, boss checklist, which sites are fully detailed at birth.
**Decisions (2026-09-24, decided):**

1. **Site types, not only dungeons:** dungeon (planned / lair / tomb / ruin / natural), stronghold-HQ (faction seat, heist), wilderness site, urban site, planar site, social site (court, festival, tribunal). **The mix comes from the content-mix dial** (item 2): politics-heavy → more social and HQ sites; exploration-heavy → more wilderness and ruins.
2. **Site directory at birth** (`design/sites.md` + registry). Per site: id, name, region, type, **danger tier (stamped)**, **room count (stamped)**, **act (stamped — the act the site belongs to, which item 13.4's later-act check keys to)** (errata 24.2 #9), **thread/trigger** (must link to a faction, NPC, quest seed or arc beat — no site exists to fill a count), payoff type (treasure / lore / ally / plot item / access), three telegraphs, escape geometry, attitude to intruders (kill / capture / enslave / ignore / negotiate / test), occupant summary (ecology), **what happens if never visited** (the occupant's own plan, wired to the simulation), reoccupation candidate, status (skeleton / detailed / played).
3. **Danger tiers are fixed and spread across the map:** T1 CR 0-2, T2 CR 3-6, T3 CR 7-11, T4 CR 12-16, T5 CR 17+. Intended-path sites match the arc's level band; off-path sites cover every tier, and **Act 1 territory always holds 2-3 sites far above the party's expected level**, telegraphed — the designed form of "a level-3 party can walk into a CR 15 site".
4. **Detail format** = the Debased Mint's four phases, as is: *Concept & ecology* / *Map* (≥2 entrances, verticality, a loop so retreat can use a different route) / *Room-by-room table* (content, category, XP math without the group multiplier) / *Content variety check* (combat ~50%, trap ~10%, special 10-15%, structural 15-20% — bands kept) + "Running this well" + Connections. Additions: telegraphs, escape, attitude, boss-checklist application, sanctuary/rest pressure.
5. **Room count is enforced on both sides.** *Design side:* `room_count` is a stamped field; `detail` cannot reduce it and the validator compares the detailed room table to the stamp (±10%). Counts derive from the XP budget and the site's role, on Ashen Crown's own distribution: **minor 5-10, standard 11-19, major 20-25, capstone 30**; by scale — short 4 minor / 3 standard / 1 major; standard 8 / 9 / 5 / 1 capstone; epic 12 / 14 / 10 / 2 capstone. The role band is the **allowed range**: for intended-path sites the XP formula of 9.6 picks the exact count inside it; off-path sites skip the formula and roll inside their band (errata 24.2 #6). *Play side:* a site is a **graph, not a list**. Each site stamps a **minimum depth** (shortest path from any entrance to the payoff room, e.g. ≥14 of 22 rooms) and the validator measures it on the room graph; loops lead back to exits, never to the payoff. A shortcut opens only when earned in play (a map, a learned secret). A **site progress record** (`site-progress.json`, the site counterpart of `tracker.json`) tracks each room as unseen / seen / cleared / skipped; the DM marks rooms as the party enters, `save` reports "Bonewrights' Hall: 6/22 rooms", and "skipped" requires a reason (the party's chosen route bypassed it) — an unreasoned skip shows in the validator. This also answers "which room were we in" after a context compaction.
6. **XP budget:** total XP for the level band is computed; intended-path sites carry ~70% (the rest from social / exploration / travel). Site budget ÷ the tier's average room XP = room count, clamped to the site's role band from 9.5 (errata 24.2 #6). Off-path site XP is outside the budget; whoever enters earns it, and their room count is rolled inside the role band rather than computed.
7. **Loot budget:** `loot-budget.yaml`, per tier a gp range + item counts by rarity (SRD's 362 items carry rarity and attunement). Doctrine unchanged: the boss carries and drops a signature weapon + a defensive item; support creatures drop nothing; plot payoff items are `item_` entities.
8. **Ecology from the SRD:** `monster-ecology.yaml` (habitat tags, social role leader / elite / minion / ambient / solo, faction affinity) + reskins via "Modifying Creatures"; custom creatures are `creature_` entities with a full stat block written at detail time; the signature creature appears in sites. Hazards from `09-running` by tier (traps, diseases, poisons, madness).
9. **Boss and the reconciliation with "the world does not scale":** the encounter-design checklist is mandatory, but `burst_check.py` runs against a **reference party at the tier's intended level**, never the actual party. A CR 15 boss is built so a level-15 party cannot end it in one round; a level-3 party dies, a level-18 party steamrolls it, both accepted. The self-feeding reward loop is known at design time (intended-path loot is known), still inside the tier. This changes `SKILL-encounter-design.md`, noted under item 21.
10. **Fully detailed at birth:** the first 2 / 3 / 3-4 sites (item 2's numbers, by scale) on Act 1's intended path (errata 24.2 #6). The rest are skeletons until `detail` on approach.

**Critique pass questions:** "Which thread ties this site to the game, and what has it done 60 days from now if the party never comes?" and "How does a party know this place's danger before stepping in?"

### 10. Story arc
**Question:** acts/chapters by scale, consequence-shaped beats, threat escalation, hub-and-spoke nodes per chapter, quest seed bank, hook sockets, "if the party never arrives".
**Decisions (2026-09-24, decided):**

1. **Two layers: spine and situations.** *Beats* are the spine — mandatory **consequences** (something different in the world, never an event). *Chapters* are situations — hub-and-spoke nodes entered in any order. By scale: short 1 act, 3 beats (inciting / midpoint shift / resolution), 3 chapters; standard 3 acts × 2 beats = 6, 6-8 chapters; **epic keeps 6 beats** with 9-12 chapters — the spine does not lengthen, the world around it widens.
2. **Beat format** (the existing dynamic-arc format plus three additions): id, label, `what_changes` (consequence-shaped; the critique pass rejects "X happens" wording), `world_pressure` (**bound to a front step from item 7**, i.e. a real `factions.json` operation step, not prose), telegraph scene, **2-3 delivery paths** (which site / NPC / event can land this consequence), **pre-written pre-emption fallbacks** (cost / secondary / deferred, all three written at birth), status.
3. **Reconciliation with the immutable bible.** The arc's *design* lives in the bible: theme, resolution, acts, beats, delivery paths, fallbacks. `state.md → Campaign Arc` holds only the **pointer and status**: current beat, steering notes, completion records. When a beat is pre-empted the DM does not rewrite the bible with `arc revise`; it **picks one of the three designed fallbacks** and logs the choice in `revision_log`. That play-time command is named **`arc fallback`** (`arc revise` is retired), so that `revise` means a change of canon only (errata 24.2 #7). `arc new` (after 3b) is a birth-lite run of the designer itself, with the user's approval.
4. **Chapter format:** id, title, locations (registry), level band, drive, intended-path sites (item 9), key NPCs, **3-5 nodes** (what is here, what is at stake, ways in, **what happens if the party never arrives** → wired to the simulation), the act's A/B scenario (item 7), a content-mix check against the dial (site / social / exploration ratio), its share of the XP budget.
5. **The threat escalation table** (world.md's five stages) is driven by BBEG front steps; a stage advances when a step completes, not on DM feel. Under the simulation charter (item 7 §7) the step resolves in the deterministic engine, the doom day behind stage 5 is fixed at birth and moves only through a party-caused structured block, and the current stage is an overlay value (errata 24.2 #2; 24.6 #3).
6. **Quest seed bank:** by scale (6-8 / 15-20 / 30+); each seed = hook + complication + resolution + reward, tied to ≥1 NPC/faction, a `seed_` entity; about half tied to sites, half standalone. Ashen Crown's "none left abstract" rule is a validator check: every seed has a concrete written outcome.
7. **Hook sockets** (`socket_`): typed slots, party size × 3 (party size × 2 in `short`) — "a PC in debt to faction X", "a PC whose family was at event Y", "a PC trained under NPC Z". Each socket points at a node and an NPC; the socket NPC is drawn from the existing roster, never added on top of it (errata 24.2 #3; 24.6 #4); filled in item 12.
8. **Planted hooks** (Chekhov's guns): **3-5 per act** at birth (an object, a line, a signpost) with payoff hint and status, in Ashen Crown's `planted-hooks.md` format. A check flags any hook unresolved for 25+ days (`foreshadowing_check.py` is rewritten from its description in the original repo — no code for it exists in the archive) (errata 24.2 #15).
9. **The big secret's three clues** (item 4) must be placed: the validator checks each clue is tied to a site or NPC and that the act order is right.
10. **Endings are designed at birth:** win / loss / pyrrhic, each consequence-shaped, each with a "world after" (epilogue seeds, the seed of a possible next arc).

**Critique pass questions:** "How can the party trigger this beat by three different routes? One route means it is a plot, not a situation." and "If the party never enters this act, what does the world do?"

### 11. Player primer and knowledge layering
**Question:** what a character raised in this world knows, how DM-only facts are marked, how this feeds the source-of-knowledge check.
**Decisions (2026-09-24, decided):**

1. **Three tiers on every fact:** `public` (anyone raised here knows), `discoverable` (takes effort: a check, an NPC, a document), `secret` (DM-only until surfaced in play). The registry carries the tier; every prose file uses the same three headings (*Public / Discoverable / Secret*) so extraction is mechanical.
2. **DM-only is a mirror folder.** `design/dm-only/` mirrors the bible's paths: `design/npcs/npc_x.md` carries only the public and discoverable sections, its secret section lives at `design/dm-only/npcs/npc_x.md`. The user's free-reading surface is the primer, the player map, the approval cards and each PC thread's public face; everything else under `design/` outside `dm-only/` is **"DM-open, player-avoid"** (a CLAUDE.md line), and the user never opens `dm-only/`, where the canonical registry also lives (errata 24.2 #1; 24.6 #1). Validator: no secret-tier text anywhere outside `dm-only`.
3. **The player primer** (`design/player-primer.md`, markdown, the one bible summary fully open to the user): the world **as a native knows it** — regions and polities and who rules, the gods as worshipped, calendar and festivals, money and prices, languages, peoples, what everyone knows about magic and its regulator, famous places, the **taught history** (public layer of events), current rumours (the day-0 slice of the news feed), **what is considered dangerous** (the public telegraphs of over-tier sites: "nobody goes to the Black Fen"), and the player pitch. Plus the player map (item 6).
4. **Origin sets knowledge.** The primer is sectioned per culture/polity; a native of A knows less about B. At character creation the player picks an origin (polity/settlement) and that section becomes what the character knows — a new step in `character new`.
5. **Wired to the source-of-knowledge check.** Baseline = primer's public layer ∩ the character's or NPC's origin; NPC ledgers add to it; private channels via `channels.py`. The designer emits `common-knowledge.json` (keyworded public facts) so `channels.py check` can ask "is this already common knowledge?" before flagging, cutting false alarms.
6. **Backstory guidance.** The primer ends with item 10's hook sockets rephrased as **spoiler-free questions** ("Do you owe anyone in the capital?", "Where was your family during the Great Fire?") so a player's backstory lands in a socket naturally; item 12 binds it.
7. **Language of the bible: the narration language** (Turkish for this table). Code and skill stay English; campaign content (bible, primer, dm-only) is written in the language the DM narrates in, so names and terms are born in the language of play.

### 12. Character integration pass
**Question:** filling hook sockets from PC backstories, personal thread files, the equal-weight guarantee.
**Decisions (2026-09-24, decided):**

Every player gets a personal story and mission. Ashen Crown's `kriv-thread.md` (a PC thread's anatomy) and `ascension-tracks.md` (a personal mechanical track, both PCs advancing at the same rate) are the models; both were hand-written mid-campaign and rebalanced later — the designer builds them at birth.

1. **When and with what.** `design integrate` runs after all PCs are created. Input: each sheet (Pillar sentence, backstory, origin, class, alignment, answers to the primer's socket questions) + the bible (sockets, factions, NPCs, sites, timeline).
2. **A thread file per PC** (`design/threads/pc_<name>.md`, secrets in `dm-only`; the PC itself is a `pc_` registry entity that the thread and its sockets reference — errata 24.2 #14):
   - **Personal thematic question** — the campaign's question from this character's angle, distinct from the other PCs'.
   - **The truth** — something about their past or nature they do not know; pinned to a timeline event and a faction/NPC; fills a socket.
   - **Three layers** surfacing at depth: layer 1 in Act 1 (discoverable), layer 2 at the Act 1 climax / Act 2, layer 3 in Act 2-3 (secret). Each tied to a real site or NPC; the validator checks all three are placed.
   - **A personal antagonist** — an existing or new NPC, but tied to the antagonist hierarchy (e.g. the lieutenant who burned their village) so it is not a sideshow.
   - **Own sites** — ≥1 per act, on or near the intended path (from the skeleton pool or newly added within scale).
   - **Mission** — the player-facing face: what the character wants as an **active** goal ("take back / prove / destroy", never "find out who"), with a goal-tracker record (`goals.py` gains a `pc` kind) so progress is measured and thresholds fire.
   - **Personal mechanical track — only when the signature mechanic was rolled** (item 4); otherwise the mission alone. Stage gates by plot item + level floor, a cost per stage, all PCs' tracks in **one file** so they advance at the same rate (the Ascension model).
   - **Crossing points** with the other threads: **one per act** (a site where two threads meet, an NPC who matters to both); skipped for a solo party (errata 24.2 #12).
3. **Equal weight is mechanical.** The validator counts per PC: sites, NPCs, layers, beats touched, XP share of personal content; **more than 35% imbalance** between PCs is flagged; for a one-PC table the imbalance and crossing checks are skipped (errata 24.2 #12). During play, `end` keeps a spotlight ledger (scenes per thread over the last 3 sessions), giving the DM Style Notes rule data.
4. **Sockets are bound** to a PC or marked unused; unused sockets live on as NPC-driven seeds.
5. **What the player sees:** their thread's public face (mission, the people and places they know); the truth stays dm-only.
6. **PC death / new PC:** `integrate` reruns for the new PC only; a dead PC's thread becomes a world thread (its antagonist does not vanish, its open layers become seeds).

**Critique pass questions:** "Can this mission be played independently of the main road, or is it the main plot renamed?" and "Why would the other PC want to be there at this thread's finale?"

### 13. JIT elaboration during play
**Question:** the `detail` command, what triggers it, depth policy, how it respects bible constraints and the encounter-design checklist.
**Decisions (2026-09-24, decided):**

Already decided elsewhere: the DM triggers `detail` itself on approach (item 1); `detail` deepens a skeleton and never alters stamped facts (item 3); bosses are sized against a reference party at the tier's level (item 9).

1. **How "approaching" is known** — three triggers from the map graph and state: (a) the party is in the same settlement as the site or ≤1 travel day from it; (b) the party has **stated the site as a destination** (the DM records intent in a `next_session_opening`-style line in `state.md`); (c) a rumour/news record has pointed them there. Any of these puts the site on the **"detail needed"** list in `design status`; `load` and `save` print that list so it cannot be missed.
2. **The real timing is between sessions; in-session is the fallback.** `end` gains a **prep step, the way a human DM prepares**: the DM asks itself *what level is the party, where can they reach from here, what are their stated goals, what has the world just done near them* — then predicts the next session's likely sites (1-3), runs `detail` on them, and passes the results through the validator. In-session `detail` is only for an unexpected swerve: the DM says "give me a minute, I'm preparing", details before the scene opens, never once inside. Every `detail` — the prep at `end`, the mid-session swerve, the hand-called one — runs through the birth machinery (a fresh-context agent, a `_staging` fragment, `registry.py merge`, a single-entity check, ids and paths returned); the play tab never authors the file, it reads the finished file lazily, and validator output is redacted in every mode (errata 24.2 #4; 24.6 #5). **Improvising a designed site from its skeleton is forbidden** — that is the exact failure (running an improvised version of a place the table had built) this rule exists to end. The one tiered exception: a **minor, unlinked skeleton site** (room band 5-10, lore/treasure payoff, tier ≤ the party's band, no clue / beat / thread / hook reference) may be run live from its skeleton + telegraphs + escape line, is marked `played-improvised`, and is backfilled by `detail` at `end`; everything else keeps the hard stop (24.6 #5).
3. **What `detail` produces, by entity type** — each of them written by the birth machinery (fresh-context agent → `_staging` fragment → `registry.py merge` → single-entity check), never by the play tab (errata 24.2 #4; 24.6 #5):
   - **Site:** skeleton → the full four-phase file (item 9), room graph and minimum-depth check, ecology, telegraphs made concrete, loot list, boss checklist with the reference-party `burst_check`, a `site-progress.json` record opened.
   - **Settlement:** anchors already exist; the small-point budget is filled (shops, inns, district characters) with a price table from the current economy and local rumours from the news feed. **Small points are permanent** once detailed: they enter the registry as `place_` entities and never change — an inn named once is that inn forever (errata 24.2 #14).
   - **NPC:** minor → full dossier (when the player latches on), the registry `tier` field raised accordingly (errata 24.2 #14); Known Facts filled from origin and witnessed events.
   - **Chapter:** on entering a new act, that chapter's nodes are made concrete (who is where, each site's current state, everything the simulation has done up to that day applied).
   - Factions are complete at birth; `detail` does not touch them.
4. **What the elaborator reads** — the constraint matters as much as the quality: the registry entry + stamped facts + connected entities (2 hops) + the news feed and simulation state to date + the relevant `state.md` section + the matching `dm-only` file + `SKILL-encounter-design.md`. **It never reads or spends later acts' content**: an Act 1 site cannot hold an Act 3 payoff (validator: no entity referenced by a detailed site may be stamped to an act later than the site's own stamped `act`, item 9.2) (errata 24.2 #9).
5. **A critique pass at detail time too.** For a site: "three things that could exist only here" and "what a party three levels early sees, and where it runs". Then `design check` runs for that entity only (fast, not the full validation).
6. **Record.** Every `detail` call is logged in `design.json` (when, in-world day, which trigger); the skeleton snapshot is kept for the stamp comparison.

### 14. Revision
**Question:** the `revise` command, revision log, stale-prose detection via the registry, arc-bending rules.
**Decisions (2026-09-24, decided):**

Already decided: the bible is immutable during play, the DM never calls `revise`, arc pre-emptions resolve through pre-written fallbacks (items 1, 10).

1. **Two different things, kept apart.** *What happens in the world* (a town burns, a leader dies, the party betrays a house) is not a bible change; it goes to `state.md`, `factions.json`, `goals.json`, the graph and the news feed — the bible holds what was designed, these hold what happened. Where the change touches a designed entity's current state (ruler, control, alive/dead, location, status, `seen_in_play`, threat stage) it is written to `design/overlay.json`, whose only writers are `simulate`, `site_progress.py`, `campaign_graph.py`, `factions.py` and `registry.py play-set`; "immutable" covers the stamped fields only (errata 24.2 #2). *A change of canon* (drop this god, give this faction another objective, move this region north) is `revise`, and only the user's call.
2. **Three scopes.** `revise` targets a **fact** (a registry field), an **entity** (remove/replace) or a **phase** (rerun, item 1's `design phase <n>`). Same flow each time: registry changes → the wiki-link scan lists affected files (item 3 paying off) → regeneration of affected files is proposed, the user approves → validator → `revision_log` gets date, scope, reason, affected-file count.
3. **Free before birth completes, constrained after.** During phase approval `revise` is free — it is the correction round itself. After session 1 every registry entity carries a `seen_in_play` flag (derived from site-progress, the graph's `discovered` edges, the session log), held in `design/overlay.json` rather than in the registry itself (errata 24.2 #2). An **unseen** entity is revised freely. A **seen** entity: `revise` warns and offers two ways only — an in-fiction explanation for the change ("the god's name had been mistranscribed all along") or refusal. No silent retcons.
4. **Revising DM-only content without seeing it.** `revise --dm-only <id> "direction"` regenerates the secret content without showing it, reporting only "changed, validator passed". The owner can intervene in canon without spoiling their own game. Because secret entities carry opaque ids, the owner addresses them by role instead: `revise --dm-only --role bbeg | big-secret | pc-truth:<pc> "direction"`, resolved script-side; and `design ask "<yes/no question>"` is the blind proxy — a fresh agent reads the dm-only projection and returns exactly `evet / hayır / spoiler vermeden cevaplanamaz`, logged in `design.json` (24.6 #6).
5. **`arc new`** (after 3b): the designer itself generates a new arc from the completed arc's resolution and the world's state on that day (existing procedure kept, now grounded in the registry and the simulation); new sockets and sites are added within scale; the old arc is archived to `## Arc History`. A birth-lite, approved like a phase.
6. **Versioning.** Every `revise` and every `detail` writes `design/` to git as its own commit (scope and reason in the message); the bible's history stays readable and rollback is possible.

### 15. Validation & QA
**Question:** the structural validator's checklist, the per-phase critique rubric, the design report.
**Decisions (2026-09-24, decided):**

The original repo once had check scripts (`dungeon_content_ratio_check`, `npc_description_check`, `npc_tier_check`, `faction_design_check`, `consequence_check`, `session_pacing_check`, `rest_check`; `name_collision_check`, `clock_check`, `solo_burst_check` already live on in the skill as `name_registry`, `calendar.py check`, `burst_check.py`). Their code is not in the archive; the ones still needed are rewritten as validator modules.

**1. Structural validator — `design_check.py`, deterministic, no LLM.** Modules run singly or all together under `check`:

| Module | Checks |
|---|---|
| `refs` | every `[[id]]` resolves; every entity's `file` exists and front-matter matches; ids unique across registry + name_registry; no first-name collisions |
| `stamps` | stamped fields equal the birth snapshot; no danger tier anywhere derived from level |
| `secrecy` | no secret-tier text outside `dm-only`; every entity has a tier; the big secret's three clues are placed in act order |
| `overlay` | `design/overlay.json` keys resolve to registry ids; only overlay fields (control, ruler, alive/dead/fled, location, status, `seen_in_play`, price modifiers, threat stage) are overridden, never a stamped one; every overlaid value carries its writer and day (errata 24.2 #2) |
| `scale` | counts within the scale band (regions, settlements, factions, NPCs, sites, gods, seeds, room distribution) |
| `map` | coordinates consistent with day counts; graph connected; every site in a region; travel-times generated from the graph |
| `factions` | per faction: fracture, secret, endgame, betrayal candidate, stance to every faction, doctrine for all six triggers (alliance / loss / gain / exposure / death / betrayal — the canonical list lives in `factions.yaml`) (errata 24.2 #5), HQ exists, operation with ≥2 dated steps, heir; BBEG front on a hard calendar |
| `npcs` | four axes, ≥2 relationships, secret + surfacing path, weakness, voice samples, stat anchor, Known Facts; demographic drift 65%; ≥2 graph edges, no islands, within 2 hops |
| `sites` | thread, 3 telegraphs, escape, attitude, payoff, danger tier, room count; if detailed: room table within ±10% of the stamp, minimum depth, content-ratio bands, no reference to a later-act entity |
| `arc` | beats consequence-shaped (forbidden patterns: "X happens", "the party finds X"), 2-3 delivery paths + 3 fallbacks per beat, world_pressure bound to a front step; 3-5 nodes and "if never arrives" per chapter; three endings |
| `threads` | per PC: 3 layers placed, antagonist tied to the hierarchy, 1 site and 1 crossing per act, imbalance ≤35%; for a solo party the crossing and imbalance checks are skipped (errata 24.2 #12) |
| `budget` | intended-path XP covers the level band (~70%); loot within the tier table |
| `signatures` | each of the three signatures in ≥3 entities; trope breaks traceable in ≥5; forbidden defaults absent in a text scan |
| `seeds` | every seed has a concrete outcome and ≥1 NPC/faction; planted hooks 3-5 per act |

Output: error (stops) vs warning (continues, reported), with entity id and a one-line reason. Full run at each phase end; single-entity run after `detail`; **a fast run (`refs` + `stamps` + `secrecy`) at every `save` that only reports and never halts the session.**

**2. Critique pass — LLM, at every phase end, before approval.** The **same model** as generation (a cheap critic gives cheap quality) but a **separate call** without the generation context: input is the phase output + that phase's rubric + the premise. The critique questions recorded under items 4-12 are the rubrics, kept in `SKILL-design.md` so every campaign meets the same bar. It returns a structured verdict: `pass` / `fix:<list>` / `rerun`. A `fix` list goes back to generation for **at most two loops**; if the phase still fails after the second, it is brought to the user as "did not pass, because…" — never silently accepted. Two additions for the blind owner: a **`wishes` rubric** runs over the dm-only text too, with a per-wish ✓ on the phase card; and the BBEG, lieutenant and premise-secret files get **two independent critics** (different rubric order, no shared notes) instead of one (24.6 #6).

**3. Design report — `design/report.md`.** One page at the end of birth: dials and the dice log, scale counts (target/actual), signatures and trope breaks, faction board summary (public), site directory status, PC sockets (empty), validator result, critique-pass records (loops per phase), total tokens/time. What the user sees for final approval is this report's public part plus the primer.

### 16. Load-time integration
**Question:** master index, location index with read-status, what `/dm:dnd load` reads and what stays lazy.
**Decisions (2026-09-24, decided):**

Two goals at once: `load` stays light however large the bible grows, and nothing designed is ever overlooked again (the Debased Mint went unnoticed until session 20; the Bonewrights' spokesperson had two names in two files).

1. **The hot path keeps its shape and loses weight.** `load` reads what it reads today (state.md, world.md, npcs.md index, characters, DM Style Notes, Pinned Facts, Live State Flags, arc pointer). But **world.md and npcs.md are generated from the registry**, never hand-edited: world.md is "the world at a glance" (public + discoverable summary), npcs.md the full index table. Both regenerate at every `save`; the registry is the single source. Both render design ⊕ `design/overlay.json`, so a ruler flipped by the simulation prints as current, with a "changed since birth" marker on every overlaid value (errata 24.2 #2). Hand notes go to the registry or to state.md, not to these files.
2. **The master index is generated, not written.** `design/index.md`, from the registry, one table per type: id, name, **aliases** (the in-play name ≠ file name problem), file, status (skeleton / detailed / played), `seen_in_play`, region, one-line summary. The location index is the same table filtered to places. `campaign_search.py` also searches the bible and the registry, so "was this name ever designed?" is one command; it excludes `dm-only/` (and with it the canonical registry) by default, searching only the public projection (errata 24.2 #1).
3. **Steps added to `load`:** (a) `simulate` for elapsed days (replacing today's `tick`) → news feed → the DM pulls the records for the party's current region; (b) `design status` → the "detail needed" list and the sites prepped at the last `end`; (c) the **current chapter's file** (`design/chapters/<id>.md`) is read, and only that one (the import lazy-corpus rule); (d) **all PC thread files are always read** (errata 24.2 #12), since they are relevant to every session; (e) the prep note from the last `end`.
4. **Lazy rules, written out:** a site file is not read before approach; an NPC dossier when a scene centres on them (existing rule); a `dm-only` file only when that scene needs that entity's secret, and separately from the voice/motive pass (the two-pass reading rule); chapter files only for the current chapter.
5. **Seen / played status from one place.** `seen_in_play` lives in `design/overlay.json`, not in the registry (errata 24.2 #2); sources are `site-progress.json` (played), the graph's `discovered` edges (seen) and the session log. The index shows it; the DM never marks "read" by hand, play marks it.
6. **state.md bloat is braked.** The designer generates a lean state.md; pasting design content into state.md is forbidden (the validator's fast `save` run **warns above 600 lines**; Ashen Crown is at 1246 today). The Continuity Archive compression rule stays; state.md carries what happened, never what was designed.

**Decisions (2026-09-24, decided):**

### 19. Pipeline mechanics
**Question:** phases, `design.json` manifest, resume/checkpoint, model routing, token cost per scale, the approval loop.
**Decisions (2026-09-24, decided).** Produced by a read-only multi-agent pass (three independent designs: reliability / cost / owner-player lens; a cost estimator that measured the Ashen Crown corpus; a synthesizer; two adversarial critics checking against items 1-18). The critics' fixes are folded in below. Full material: session task output `wwi5p3rri` (synthesis, design.json schema, cost table, 26 critique findings).

**1. The main session is a blind conductor.** It asks the Phase 0 dials, runs deterministic scripts, launches **one Workflow per phase**, shows a script-built public phase card, records approvals. It never writes bible prose, never reads `design/dm-only/**`, `design/_staging/**` or raw `entities.json`, and holds only `design.json`'s public part plus `registry.py export --public`. The conductor reads only the generated projection `design/entities.json`; the canonical registry at `design/dm-only/entities.json` is never opened by it (errata 24.2 #1; 24.6 #1). Agents run with fresh contexts, write files to disk and return **ids, enum statuses, counts and paths only** (no free-text fields: a `warnings[]` string from an agent that just read a secret is a leak). All free text goes to `_staging/<phase>/<id>.notes.md` and reaches the conductor only through `design_check.py --redact` / `design_approval.py`. Enforcement: return schemas are the structural guarantee; a `design_read_guard.py` PreToolUse hook is the belt. The hook **discriminates the caller** (subagent transcripts `agent-*.jsonl` may read dm-only; the conductor's own transcript may not), is **armed per designer command** (`new`, `phase`, `integrate`, `revise --dm-only`, `arc new`, hand-called `detail`) via an `active-design.json` marker **carrying the campaign name** and a `mode: birth | detail | playtest` field, where `playtest` carries an allowlist of player-facing artifacts for item 22.5's player agent (errata 24.2 #13), and covers Read, Grep, and Bash paths (`cat`/`sed`, `campaign_search.py`, `registry.py` without `--public`, `design_check.py` without `--redact`). For the DM's own in-session `detail` (item 13) the guard arms for the duration of the detail run (`mode: detail`) and stays unarmed for the DM's reads of the finished file (errata 24.2 #4; 24.6 #5).

**Payload probe result (slice 0 B, 2026-09-24; `docs/reports/2026-09-24-payload-probe.md`).** The `agent-*.jsonl` assumption above is wrong: the conductor, an Agent-tool subagent and a Workflow agent all report the **same** `transcript_path` (the main session's), the same `session_id` and `prompt_id`, and an identical environment. What discriminates is the payload's **`agent_id` / `agent_type`** pair, present on every subagent call and absent on the conductor's. The guard therefore keys on `agent_id` presence (absent → conductor → dm-only denied while armed) and on `agent_type` for the allowlists in `active-design.json`: `birth` / `detail` admit the designer's own agent types only (custom agent definitions surface under their own name; `general-purpose` and other ad-hoc agents are denied), and `playtest` denies the player agent type (errata 24.2 #13). The `session_id` in the marker is matched against the payload so one tab's marker never governs another tab's hooks. The same test gives `dice_guard` its "agents never roll during birth" rule. The 24.1 #12 fallback is not needed; the hook tests carry both payload shapes as cases, and the probe is repeated after any Claude Code upgrade that changes the payload (desktop 2.7032.0 / SDK 0.3.280 recorded).

**2. Phase shape and roster.** Every generative phase: one **single-writer skeleton agent** (ids, stamps, matrices: stance matrix, deity web, map graph, beats) → conductor merges → **per-entity fan-out** `pipeline(write → critique → fix)` with no barrier → merge → `design_check.py --phase N --redact` → **phase-level critique** whose input is the skeleton plus each entity's one-line identity / telegraph / voice lines (cross-entity rubrics such as "regions distinct only by name?" cannot be answered per entity) → approval card. Phases: **P0** dials + public dice log + **arc skeleton derived by script** from `scale.yaml` (chapter ids, acts, level bands; breaks the sites↔arc cycle) → **P1** premise (single writer) → **P2** cosmos (single writer; separate church entities per god only in epic, the `church` field on every god at every scale — errata 24.2 #11) → **P3** lands (skeleton → one agent per region for its travel table → one per city/town, villages in fives; `map.json` → `map_render.py`) → **P4** powers (skeleton: roster, quota, stance matrix, BBEG front; one agent per faction; one for the consequence calculus; **antagonist `npc_` ids reserved as registry stubs** so `goals.py add` resolves) → **P5** people (skeleton: roles/tiers, species/gender/name candidates rolled by script; one agent per major/supporting NPC, minors in sixes) → **P6** sites (skeleton: directory with stamps; one agent per birth-detailed site with the reference-party `burst_check`) → **P7** arc (skeleton: beats, endings, sockets; one agent per chapter; seeds in sixes) → **P8** primer and close (one agent per culture section; indexes, `world.md`, `npcs.md`, lean `state.md`, `report.md` by script; full validation; final approval = public report + primer) → **P9** `integrate` after `character new`, same machinery, outside birth. Phase-order note: the P0/P3 skeleton reserves `polity_` ids and `npc_` stubs for rulers, anchor-location owners and village NPCs (filled by P4/P5); the per-phase validator accepts `status: pending` on an entity owned by a later phase; only P8's full run demands that every file exist (errata 24.2 #10).

**3. Single-writer stores and the staging protocol.** `entities.json`, `factions.json`, `goals.json`, `graph.json`, `map.json` are never written by a fan-out agent. Each agent writes its prose file **first** and a staging fragment `_staging/<phase>/<id>.json` **last**; the fragment is the commit record (it names the prose path and byte size; prose without a fragment is treated as absent). The conductor runs `registry.py merge --phase N` (upsert by id, temp file + `os.replace`, refuses stamped-field changes unless passed a `--revise <log-id>` token) and `design_seed.py --phase N` (idempotent wrapper over `factions.py` / `goals.py` / `campaign_graph.py` / `channels.py` / `calendar.py`, with a `seeded[]` ledger). The stores gain atomic writes (today `factions.py` and `goals.py` overwrite in place) and `goals.json` gains a `_meta` block. **Secret entities get opaque slugs** (`npc_s07`, assigned by the skeleton script); their names live only in the dm-only projection, so labels, `args` and the Workflow progress tree carry nothing readable. `name_registry add` and `used.json` rows are written **only at phase approval**; `design abandon` retires them. `design_revise.py` is the second sanctioned writer of stamped fields (it re-baselines that entity's stamp snapshot and logs the revision). In-play `detail` follows the same staging protocol: the agent writes the prose file, then a fragment under `_staging/detail/<id>.json`, and the conductor-side `registry.py merge` is the only path into the registry (errata 24.2 #4; 24.6 #5).

**4. Manifest and resume.** `design.json` (schema in the task output; written only by `design_manifest.py init | reconcile | pending | mark | approve | stale | tokens | status`, atomic) holds `_meta` (schema_version, campaign, ruleset, lang, mode birth|play, git_root), `dials` (+ `concurrency` default 8, `economy` false), `seed` (master + per-label derivation), `arc_skeleton`, `dice_log` (public rolls), `dice_log_secret` (labels and count only; results in `dm-only/dice-log.json`), `phases[N]` (status, attempt, skeleton status, critique loops, validator, approval rounds with card and registry sha256 and commit, `directions[]`, tokens.out delta, stale_reason), `entities[id]` (phase, status pending|staged|merged|validated|critiqued|failed, file, stage_file, attempt, critique_loops, last_error), `seeded[]`, `detail_log`, `revision_log`, `totals`, `validator_last`. **Disk is truth, the manifest is the index, the Workflow journal is an accelerator** (valid within one conversation). Before every run: `reconcile` (merges every well-formed fragment, repairs statuses) → `pending --phase N` (roster minus ≥merged, **with each entity's absolute file list under a 2-hop read budget**; no agent ever reads "everything") → passed as Workflow `args`. Rerun unit = entity when the skeleton is merged, the whole phase otherwise. During birth `design phase <n>` bumps `attempt`, archives `_staging/N` and marks later phases `stale`; `load` refuses until birth reaches final approval. **In play** a phase-scope revise is executed as entity-scope regeneration of the affected files; later phases are marked `needs-check`, `load` prints a banner, the fast `save` check carries the warning, nothing blocks play.

**5. Failure handling.** Agent returns null → retry once with the attempt number **in the prompt** (labels are display only), second null → `failed`; a phase with failed ids is shown but **cannot be approved** (rerun the pending list, or drop the entity via `revise` and approve). Critique null → `critique_missing`, listed on the card, approval allowed with the count shown. Validator errors → targeted fix agents within item 15's two loops, then "did not pass, because…"; when the failure is dm-only-only the card says "failed on N dm-only criteria" with the count, and the user picks rerun / `revise --dm-only` / approve-as-is. Rate limits → fan-outs chunked in slices of `concurrency`. Main-session compaction → after every Workflow return the first actions are `design_manifest.py mark` / `tokens` (the manifest has no `update` verb, item 19.4) and a git commit, before any text to the user (errata 24.2 #16).

**6. Approval loop.** One Turkish **phase card** per phase from `design_approval.py`, built from the public projection only (never from agent returns); the `secrecy` validator runs on the card itself. Contents: counts vs scale band, names with culture and one public line, the player SVG (P3), redacted validator summary, critique loops used, failed ids, tokens/minutes, a "what a native knows" excerpt, and on a rerun a diff against the previous card. **Hidden entities are not shown in any form**; the scale-band check runs script-side with the full count and the card only says "scale band ✓". The premise card carries a **spoiler-safe abstract** of the secret layer — archetype class, novelty vs `used.json` yes/no, clue count per act, critic agreement — and the per-wish ✓ of the `wishes` rubric (24.6 #6). A correction is one sentence: the conductor classifies it as fact / entity / phase (item 14) **or as a tonal direction**, which is stored in `phases[N].directions[]` (or amends `dials.wishes` for world-wide directions) and appended verbatim to every rerun prompt; the seed is kept unless `--reseed`; an ambiguous one-word correction gets one clarifying question. Affected entities rerun (Agent tool for ≤3, Workflow for more), then validator, critique, card diff. **Max 3 rounds per phase**, then approve-as-is or `phase <n> [--reseed]`. **"Approve" requires the explicit word `onay`** (a casual "tamam" never advances a phase); recorded with timestamp, card sha256, registry sha256, the rounds, and a git commit. **After approval the conductor waits for an explicit `devam`** before launching the next phase (usage window, and a wrong correction is never spent unasked).

**7. ### 22. Testing strategy
**Question:** test campaigns per scale, uniqueness checks between them, first-session playtest.
**Decisions (2026-09-24, decided).** Existing: two hook tests (`test_dice_guard.py`, `test_skill_edit_guard.py`); pytest not installed, so stdlib `unittest` stays. Five layers, cheapest first, each a precondition of the next.

1. **Unit tests (deterministic, no LLM)** under `.claude/skills/dnd/tests/` with fixture bibles, run by `scripts/run_tests.py` (`unittest discover`): `design_dice.py` (same seed+label → same roll; order independence; `used.json` exclusion; secret rolls routed to dm-only); `registry.py merge` (upsert, stamped-field refusal, atomic write, fragment-as-commit, `--revise` token); `design_manifest.py` (crash scenarios → correct `pending`); `design_check.py` (a good fixture passes; a set of broken fixtures each trips **exactly one** module: dangling wiki-link, secret text outside dm-only, stamp change, missing telegraph, room-graph minimum depth, >35% thread imbalance, >65% demographic drift, event-shaped beat wording, seed without outcome…); `map_render.py` (shortest-path travel times, hub rule, coordinate/day consistency); `design_seed.py` (double run, one result); `factions.py simulate` (deterministic on a fixture board with seeded dice; cascade cap; brake when a party asset is targeted; news records; succession on a leader's death; stance drift and decay); hooks in both directions (conductor denied, `agent-*` transcript allowed, another campaign's dm-only untouched, marker per command); `build_design_index.py` (every one of the 334 monsters has an ecology row); table schema tests (every `data/design/*.yaml` row has id/label/hooks, ids unique, `rubrics.yaml` covers every phase, `scale.yaml` matches the plan).
2. **Dry-run birth (LLM, cheap):** one `short` campaign, fixed seed, `--economy`, end to end. Measures: calibration of item 19's token/time numbers; an **automated leak test** (no sentence from any dm-only file may appear in any conductor-visible artifact: cards, report, `world.md`, `npcs.md`, primer, `design.json`, Workflow returns, progress labels — a script greps); a **resume test** (kill mid-phase, resume, assert no duplicate entities).
3. **Test campaigns and uniqueness — `short` scale only.** Standard and epic are not generated for testing; the pipeline's counts scale by table, and the short runs plus the unit tests carry the risk. Two `short` campaigns with different seeds; script checks between them (zero name overlap via `name_registry`, zero shared table rows via `used.json`, different map graphs and demographics) plus an LLM judge on the premises ("could these be the same campaign?", "the three sentences true only here" — item 4's rubric across campaigns) and the forbidden-defaults scan on both.
4. **Quality panel (LLM judges)** on one short campaign: independent judges score each phase against `rubrics.yaml` without the generation context, plus two special judges — **human-DM readability** (can session 1 be run from the primer + chapter 1 + the first site alone?) and **load lightness** (total tokens read at `load` under a budget, e.g. 40k).
5. **First-session playtest with a player agent.** A throwaway `short` campaign's session 1 is run in a play tab by the DM (the main session, `/dm:dnd load`) against a **player agent**: a subagent with a persona and the PC's sheet, spawned each turn with the player-facing transcript so far (it may read only player-facing artifacts — primer, its own sheet, the transcript — never `design/` or `dm-only/`) and returning the player's next message in the narration language. The player agent runs under `active-design.json` `mode: playtest`, whose allowlist confines it to those player-facing artifacts even though it is an `agent-*` transcript the guard would otherwise admit (errata 24.2 #13). After the session, judges read the transcript against a checklist: opening bang, dice ownership, room-by-room play, `detail` on approach, the prep step at `end`, the simulation's first week and its news, spotlight ledger, no leak, calendar advanced per scene. The user reads the transcript too. Findings go to `dev-queue.md`; the real campaign is never the first test. (The agent is a smoke test: it cannot measure fun; the user's own first real session is the true playtest.)
6. **Storage:** test campaigns under `campaigns/_test-*/`, gitignored; only small fixtures are committed.

### 23. Migration
**Question:** whether Ashen Crown adopts the entity registry or index layout, or is left as is.
**Decisions (2026-09-24, decided): Ashen Crown stays as it is; v3 must remain compatible with it.**

The 2024 removal leaves the `**Ruleset:** 2014` header as a harmless stamp. Registry-generated `world.md` / `npcs.md` apply only to campaigns with a registry; Ashen Crown's stay hand-maintained.
- **When the campaign ends** it is moved to an **`old-campaigns/`** folder at the project root (read-only archive, like `original-repo/`), not deleted and not left under `campaigns/`. Its `state.md` then can no longer be confused with a live one.

### 25. The P1 foundation
**Question (owner, at `_test-dry-4`'s P1 review, 2026-09-27):** every birth's premise landed on the same ground. P1's rolls are abstract and the concrete ground is left to the writer. How does P1 become a foundation every later phase builds on?

**Diagnosis (six births: the public projections, dice logs and naming files; `docs/reports/dry-run-3.md` §3.2).**
- In six births every P1 table (tension, break, the three signature sub-tables) drew six different rows. The tables pointed there too: the signature seeds' examples ("a common substance (salt, ash, wax, ice)"), mutation prompts about ownership and cost, lexicon glosses (`tide` "debt", `lamp` "mourning"), history rows (`age_silence`, `age_dimming`, `age_lanterns`, `age_reckoning`, `evtype_silencing`). - Nothing measured the repetition. The critic shares the attractor, and ae6786b's "earlier campaigns" block is a prompt steer (RC-11) that primes what it names.

**The principle (the owner's building).** P0 is the project: how big, how dark, how magical, which era, how deadly, what kind of play. P1 is the foundation, P2-P8 are the floors, and play is living in the building (its upper floors stay open to renovation). Three rules:
1. Every seed is a column: at least two later floors are built on it. A seed no floor rests on is decoration.
2. No floor decides in the air: every roll of a later phase is conditioned on a seed below it or declared free texture.
3. Every floor is inspected: the promise ledger (errata 24.2 #23) carries each column up and checks it at the floor where it is due.

Seed criteria: load-bearing; a situation, not a mood; concrete (a native can point at it); linked to the other seeds by fixed homes; carries its own expansion; passes the legend test (it can be part of a story carried across the scale's level band).

**P1 in two steps.**
- *Step 1, the foundation,* by script, no model: the rolls below in order, each conditioned on the dials and on the earlier rolls, assembled into one Turkish situation sentence. The foundation is stamped and public (it holds no secret).
- *Step 2, the identity:* the script rolls every identity piece, then the premise writer builds on the foundation, which it makes specific and never changes (below).
- Then the door (each signature carries its home seed's id, the foundation's stamps are untouched, the promises are recorded), the critics (craft only; the earlier-campaigns block moves from the writer to the critic), the card and the review stop.

**The door, the critics and the card.**

**Common rules.**
- *The script is the only arbiter of conflicts:*
  - every row carries `conflicts_with` and `requires`; a table's "heavier in" is a weight, and its "needs" or "only" is a requirement;
  - conflicts are made symmetric when the table loads;
  - the pool is filtered before each draw, against every earlier roll and in both directions; the redraw-until-ok loop goes;
  - an empty pool stops the preroll (a table fault), and a conflicting row is never kept;
  - every exclusion is logged with its reason;
  - the door rechecks the final set;
  - a model-free test rolls P1 over thousands of seeds and proves no conflicting set appears;
  - in the prose, rows carry "never" lines. The door catches the lexical ones, as `forbidden.yaml`'s patterns do; for the rest a critic records a per-promise verdict that the ledger and the gate read.

  Two present holes close with it: `table_until` keeps a conflicting row after eight tries, and the trope-break draw never checks the candidate's own `conflicts_with` against the rolls made before it (the question), so "rule by lottery" can today come with "birthright versus merit".
- A row another campaign used is not drawn again while the table has rows, and rows of the same family wait three births. Actions and scars are grammar: a used one waits three births, and a target + action pair never repeats. Palettes are not excluded.
- The attractor clusters (light and fuel, hush and bells, ledgers and tolls, the rights of the dead, courts, tides, salt) have no row in any foundation table. This is a table decision, not a word ban; #18 stands.
- The dials weight rows: era, tone, magic, scale.
- No `forbidden.yaml` default: a living choice behind every break, no "Empire", no inherently evil people, no whispering advisor, no evil cult.

**Rejected on the way (not to be proposed again).**
