# Item 19 — Pipeline mechanics (merged proposal)

Governing rule, where A, B and C all agree: **the main session is a blind conductor.** It asks the Phase 0 dials, runs deterministic scripts, launches one Workflow per phase, shows script-generated public cards and records approvals. It never writes bible prose, never reads `design/dm-only/**`, and never receives a secret in an agent return value, because no agent return schema has a field that can carry one. Items 3 (one registry as shared memory), 4/11 (owner never sees dm-only) and 1/14 (bible immutable in play) are the tie-breakers below.

## Q1. Who is the designer process

**Recommendation** (C's three roles, A's and B's mechanics):
- *Main session*: P0 dials, every approval gate, corrections, scripts. It holds only `design.json`'s public part, `registry.py export --public` (a projection with no `secrecy: secret` entity or field), redacted validator output and the workflow's returned public card.
- *One Workflow run per generation phase* (P1-P8): fresh-context subagents write their prose file plus a registry fragment to disk and return `{entity_id, name, public_summary, counts, files_written[], warnings[]}`. The ≤2 critique/fix loops of item 15 run inside the script as a deterministic `pipeline(write, critique, fix)`; fix lists, which name secrets, never surface. Secret prose exists only on disk.
- *Python scripts* for dice, merge, validate, seed, render, manifest, approval card.

Why one Workflow per phase and not per birth: a workflow cannot pause for the user, and the gate is a conversation (all three). Why not the main session generating as today's `/dm:dnd new` does (`SKILL-commands.md` lines 9-51): an epic bible is ~280k visible output tokens (estimator), several compactions' worth, and every secret would sit in the transcript, so item 4 would rest on the model remembering a rule for hours (C).

Enforcement is mechanical and matches the project's existing `PreToolUse` hooks (`dice_guard.py`, `skill_edit_guard.py` in `.claude/settings.json`): a `design_read_guard.py` hook denies `Read` (and best-effort `cat`/`sed` in Bash) of `design/dm-only/**`, `design/_staging/**` and raw `design/entities.json` while `<runtime_dir>/active-design.json` exists (B's marker, the `autosave_checkpoint.py` `active-campaign.json` pattern). It lifts when birth ends: in play the DM session must read dm-only (item 16.4). The structural guarantee is the return schemas; the hook is the belt.

**Alternatives.** (a) Main session with a "write secrets to files, do not narrate" rule: cheapest, not compaction-safe, secrecy by discipline; rejected. (b) Agent tool without Workflow: kept as the fallback ladder when Workflow is unavailable and as the tool for ≤3-entity corrections (B, C); slower, same secrecy, no journal.

A spine or a matrix (stance matrix, inter-deity web, map graph, beats) is single-writer; dossiers fan out.

**Single-writer stores.** `entities.json`, `factions.json`, `goals.json`, `graph.json` and `map.json` are never touched by a fan-out agent (A, C). Each agent writes its prose plus `design/_staging/<phase>/<id>.json`; the conductor runs `registry.py merge --phase N` (upsert by id, temp file + `os.replace`, refuses stamped-field changes outside a phase rerun) and `design_seed.py --phase N` (idempotent wrapper: existence check by id plus a `seeded[]` ledger, A + C). This is required, not optional: `factions.py _save` (line 97) and `goals.py _save` (line 76) overwrite in place, `goals.json` is a bare list, `campaign_graph.py add-node` refuses a duplicate id (line 218), `channels.py add` refuses a duplicate (line 101).

**Alternative.** B's `--replace` upsert flags on every store script, with agents calling them directly under worktree isolation. Worktrees do not merge JSON and cost setup per agent; five scripts would need changes instead of one wrapper. Rejected, but the atomic-write fix to the stores (Q9) is taken from it.

## Q3. `design.json` manifest and resume

Schema in the companion block. Resume rule (A's phrasing, all agree): **disk is truth, the manifest is the index, the Workflow journal is an accelerator.** Before every run the conductor calls `design_manifest.py reconcile --phase N` (scans `_staging/N/` and the prose paths, repairs entity statuses, so a crash between file write and manifest update is harmless), then `pending --phase N`; the work-list is passed to the Workflow as `args`, necessarily, since scripts have no filesystem access. A crashed fan-out reruns only entities not `merged`; a crashed single-writer phase reruns whole (small, one author). Idempotent by construction: merge is an upsert, seeding is ledgered, rolls are keyed by label (Q8). `design phase <n>` bumps `attempt`, archives `_staging/N` to `N.attempt-k/`, marks later phases `stale`; `load` refuses while any phase is stale or unapproved (C). Within one conversation `Workflow({scriptPath, resumeFromRunId})` replays the journal prefix; across conversations only the disk is relied on.

## Q4. Checkpoint granularity and failure handling

Granularity: **entity** in fan-out phases, **phase** for single writers, **approval** for git. An agent's contract is "files on disk, then return"; the return is not the checkpoint (A, C).
- Agent returns `null` (skip or terminal API error, per the Workflow contract): retry once with the attempt number in the label so the journal does not serve the cached null (B, C); second null → `failed`. A phase with failed ids is shown but **cannot be approved** (A): rerunning the pending list is one cheap command, while an approved faction with no dossier would break `refs`. The user may instead drop the entity (`revise` entity scope) and approve.
- Validator errors: grouped by id; targeted fix agents (file + error lines + rubric) count toward the two loops; then "did not pass, because…" (item 15).
- Rate limits: the Workflow retries internally; fan-outs are chunked in slices of `concurrency` (dial, default 8) so a 429 storm hurts one slice (C).
- Compaction of the main session costs nothing: after every workflow return the first actions are `design_manifest.py update` and `git commit`, before any text to the user (A); `design status` re-orients from `design.json` + `active-design.json`. Compaction inside an agent cannot happen at ≤25k input.

## Q5. Approval loop UX

Per phase one **phase card** (Turkish), built by `design_approval.py` from the public projection only, never from agent returns; the `secrecy` validator runs on the card itself (B). Contents: counts vs scale band (target / actual / ok), names with culture and one public line, the player SVG (P3; the DM SVG path is stated, not opened), validator summary by module (redacted), critique loops used, failed ids, tokens/minutes, a "what a native knows" excerpt (C), and on a rerun a script diff against the previous card (A). Never: a secret entity's existence, secret fields, fix-list text; dm-only critique notes go to `dm-only/critique/<phase>.md` (C).

A correction is one sentence. The conductor classifies it into item 14's scope (fact / entity / phase), runs `design_revise.py plan` (registry change + wiki-link scan), echoes the public diff ("region_kul → 'Kül Ovası'; 3 files affected. Apply?"), then reruns only the affected entities (Agent tool for ≤3, Workflow for more; B), validator, critique, card diff. Secret-directed corrections go blind via `revise --dm-only` and report "changed, validator passed". **Max 3 rounds per phase**, then approve-as-is or `phase <n> [--reseed]`. "Approve" is only the user's own word in chat, recorded by `design_manifest.py approve` with timestamp, sha256 of the card and of the registry snapshot, the rounds list, and a git commit `design(<campaign>): P<n> approved`.

**Alternative.** Interleaved per-entity approval: finer, but ~40 prompts in epic; rejected (A).

## Q6. Model routing

Generation and critique **inherit the session model** (C; the Workflow tool's own guidance is to omit `model`), effort `high` for premise, skeletons and arc, `medium` for dossiers and fixes. Critique is a separate `agent()` with no generation context, input = files + `rubrics.yaml` row + premise, returning `{verdict, public_notes[], dm_only_notes_file}`. `SKILL-design.md` states that `new` is started in an Opus-tier session (today's rule for `new`) and the conductor warns if it is not. An opt-in **`--economy`** dial (A) routes fan-out dossiers and *their* critique to the current Sonnet tier, same model per tier, so item 15 holds (B). Haiku only for `report.md` prose; indexes are scripts. SKILL.md's Model Routing ids are a generation stale (`claude-opus-4-6`, `claude-sonnet-4-6`, `claude-haiku-4-5-20251001` versus the current `claude-opus-5`, `claude-sonnet-5`, `claude-haiku-4-5`); refresh under item 21 (C).

**Alternative.** B's default, Sonnet for all fan-out: roughly 40% cheaper on the merged numbers, but the bible is written once and read for dozens of sessions, and NPC and antagonist depth is what the user has repeatedly flagged. Item 22's tests can flip the default.

## Q8. Dice and reproducibility

`dice.py` rolls unseeded `random.randint` (line 118) with no log; `oracle.py` already injects a `random.Random` (lines 109-217). Give `dice.py` an injectable rng / `--seed` and add a `design_dice.py` wrapper deriving `random.Random(f"{master}:{phase}:{table}:{label}")` per **labelled** roll (C; A's hmac and B's sha256 are the same idea): order-independent, so resume, reorder and parallel agents cannot desynchronise. Rule: **agents never roll**; `designer.py preroll --phase N` makes every roll before the phase's agents start (C), which also fits the Workflow rule that scripts have no `Math.random`. Public rolls go to `design.json.dice_log`; secret rolls (which `secrets.yaml` archetype, BBEG visibility) go to `dm-only/dice-log.json`, and the manifest keeps only labels and a count (C). Phase 0 rolls are all public dials, so item 2's "seen live" holds. Reproducible from seed + the same `used.json`: every dial fill, every table row, all counts, species/gender draws, site tiers and room counts, SRD candidate lists (deterministic filter + seeded shuffle, B), name candidate lists. Not reproducible: prose, the LLM's choice among candidates, coordinates, relationship edges, mutated names. Reruns replay from the log; `--reseed` rolls a fresh sub-seed.

## Cost table (synthesizer, corrected)

Source: the cost estimator's per-unit derivation (byte counts of the Ashen Crown corpus, inflated to the plan's richer formats). I re-added every phase sum, the critique/regen lines, the input totals and the call counts; **the arithmetic is internally correct** (e.g. short 2,500+5,400+8,100+19,500+9,600+9,400+7,800+3,800+5,300+9,700+1,500 = 82,600; standard 169,200; epic 279,050; inputs 27×15k+7×15k+191k = 701k, 46×20k+9×20k+321k = 1,421k, 74×25k+12×25k+486k = 2,636k). Four **modeling** corrections are applied in the extra rows.

| scale | output tokens (visible, gen + critique + regen) | input tokens (raw, uncached) | agent calls | wall-clock (machine, excl. approval waits) |
|---|---|---|---|---|
| short | ~103k (82.6k gen + 8.0k critique + 12.4k regen) | ~0.70M | 48 as modeled (27 gen + 14 critique + 7 regen); **~70 with per-entity critique** (merged design, estimator's own caveat) | 58 min (estimator) → **1-2 h** realistic |
| standard | ~204k (169.2k + 9.3k + 25.4k) | ~1.42M | 69 → **~120** | 75 min → **1.5-2.5 h** |
| epic | ~332k (279k + 11k + 42k) | ~2.64M | 102 → **~190** | 90 min → **2-3 h** |

Corrections and assumptions:
1. **Thinking tokens are billed as output and are not in the estimate.** With adaptive thinking at `high`/`medium` effort, billed output is plausibly 1.5-2× the visible figure (Design C assumed 2×). Budget for it; the visible bible size is unchanged.
2. **Item 12's threads (`integrate`) were counted inside birth** (5.3k / 7.75k / 10.2k output, ~3 agents per scale). In the merged design it is P9, after `character new`; birth-only totals are that much smaller.
3. **Critique was modeled per phase** (14-16 calls). The merged design critiques per entity inside `pipeline()` for fan-out phases plus one phase-level pass for the skeleton; per the estimator's own caveat this roughly doubles call counts (~70 / ~120 / ~190) while token totals change little, because each critique reads one entity instead of the whole phase.
4. **Harness overhead** (system prompt, tool schemas, CLAUDE.md, memory; ~8k per call) is excluded: roughly +0.4M / +0.55M / +0.8M raw input at the modeled call counts, more at the per-entity counts. Prompt caching is not modeled; the shared prefix (rules, premise, rubric) caches well, so billed input is materially below the raw figure.
5. Wall-clock assumes 1.5k output tok/min per agent (optimistic for Opus-class Turkish prose, the estimator says so), 0.5 min latency per sequential call, ≤10 concurrent; effective parallelism only ~1.8-2.5 because the critical path is the single-writer skeletons. The realistic band doubles the estimator's number. Approval waits dominate real elapsed time: standard and epic span 2-4 sittings.
6. Sanity anchor: Ashen Crown's hand-built bible-equivalent ≈ 230k tokens (72 site entries, 21 detailed, 86 dossiers, 13 factions, 3 full dossiers) sits between the standard and epic estimates.

Money (price sheet cached 2026-06-24 in the `claude-api` skill, first-party API rates; look up at run time before quoting to anyone): Opus 5 $5 / $25 per MTok, Sonnet 5 $2 / $10, Haiku 4.5 $1 / $5, Fable 5.1 $10 / $50. All-Opus-5 on the raw figures: short ≈ $6, standard ≈ $12, epic ≈ $22; with correction 1 (×1.5-2 on output) ≈ $7-9 / $14-17 / $26-30; harness overhead adds ≈ $2-4 before caching. `--economy` (≈65% of tokens on Sonnet 5) is ≈40% less. On a Claude Code subscription the binding constraint is the usage window, not dollars (Design C), which is another reason for chunked fan-outs and phase gates.

## Disagreements between the three designs and how they were resolved

- **Model routing under item 15's same-model-critique rule**
  - positions: A: Opus for all generation, critique and fixes; optional --economy dial; B: Opus for premise and skeletons, Sonnet for all fan-out dossiers and their critique (same model per tier); C: inherit the session model everywhere at high effort; Haiku tier for assembly/index/report and minor-NPC batches
  - resolution: Inherit the session model (C, which is also the Workflow tool's own guidance) with SKILL-design.md stating that `new` is started in an Opus-tier session; `--economy` (A) is the opt-in that applies B's split. Reason: dollar difference on standard is ~$5, the bible is read for dozens of sessions, and the user has flagged NPC/antagonist depth as what matters. Haiku only for report prose since indexes are scripts (B). Alternative: B's split as default, ~40% cheaper, revisit after item 22's tests.
- **Where the critique/fix loop runs**
  - positions: A: once per phase after merge, with targeted per-entity fix agents driven by validator/critique output; B and C: per entity inside pipeline(write, critique, fix) with no barrier, plus the skeleton critiqued once
  - resolution: Both levels: per-entity inside the pipeline for fan-out phases (items 8 and 9's rubric questions are per-entity, and no barrier means idle slots are used) plus one phase-level critique of the skeleton (item 5/6's questions such as 'are these regions distinct only by name' are cross-entity). Cost: call counts roughly double per the estimator's caveat, token totals barely move. Alternative: A's phase-level only, fewer calls but the whole phase output in one critic's context and a barrier before it.
- **Registry and store writes from fan-out agents**
  - positions: A and C: agents write prose + a per-entity fragment under a staging dir; conductor runs a single-writer merge (upsert, atomic) and an idempotent seeding wrapper with a ledger; B: add --replace upsert semantics to factions.py/goals.py/campaign_graph.py/channels.py/calendar.py and let agents call them directly
  - resolution: Staging + merge + `seeded[]` ledger (A, C). The stores are not upsert- or crash-safe today (factions.py _save line 97 and goals.py _save line 76 overwrite in place; add-node refuses duplicate ids; goals.json is a bare list); one wrapper is less invasive than five script changes, and fragments make partial-fan-out recovery a directory scan. **Caveats:**
- Byte-based measurement overstates Turkish tokens by ~8%: Turkish special characters are 2 bytes in UTF-8 (npcs-full.md is 185,213 B but 170,837 chars). The 3.3/4.0 chars-per-token rules of thumb are themselves ±20%; agglutinative Turkish may tokenize closer to 2.8-3.0 chars/token on some tokenizers, which would push Turkish-output estimates up.
- JSON (registry, map.json, factions.json rows, graph edges) tokenizes at roughly 3 chars/token in practice because of punctuation and keys; the 4.0 used for JSON groups and the ~100 tok/entity registry unit may be 25% low.
- The plan's formats are richer than Ashen Crown's hand-built ones (4 dossier additions, ~13-field site skeletons, telegraph/escape/attitude sections, doctrine per 6 triggers, dated operations). Every inflation factor from measured unit to plan unit (e.g. 1,284 → 1,700 for a major NPC, 45 → 300 for a skeleton row, 3,467 → 4,200 per faction) is judgment, not measurement.
- Registry entries duplicate part of the prose (summary, key fields) so output is double-counted by ~10-15%; if the registry is script-extracted from front-matter instead of LLM-emitted, subtract most of the registry+edges line (9.7k / 23k / 37k).
- Per-agent input excludes the Claude Code harness overhead a subagent carries (system prompt, tool schemas, CLAUDE.md, memory). If that is ~8k per call it adds roughly +0.4M / +0.55M / +0.8M input. Prompt caching is not modeled; premise + procedure + registry are shared across agents and cache well, so billed input would be materially lower than the raw figure.
- Critique is modeled at phase level (item 15.2 says 'at every phase end'). Item 8's and 9's rubric questions are per-entity; if the critic is run per entity for fan-out phases, call counts roughly double (short ~70, standard ~120, epic ~190) while token totals change little.
- The fix-loop regeneration fraction (30% of a phase per loop, 0.5 loops average) is a guess; a `rerun` verdict regenerates the whole phase, and the premise phase's 'could this describe a hundred other campaigns' question is the most likely to trigger a full rerun.
- Wall-clock excludes user approval time at 9-10 gates, which will dominate real elapsed time; the 0.5 min per sequential call latency (agent startup + reading ~20k input) is an assumption, and the given 1.5k tok/min rate is likely optimistic for Opus-class generation of Turkish prose.
- Only a ~1.3k-token '/dm:dnd new' section exists today (SKILL-commands.md, 5,376 B); SKILL-design.md, rubrics.yaml and the design tables do not exist yet, so the ~6k procedure/template/rubric input per agent is an estimate of things not yet written. SRD candidate lists (item 18.2) assumed script-filtered to ~2k tokens; raw SRD YAML is 1.48 MB and must never be handed to an agent whole.
- Ashen Crown's corpus was built at levels 11-20 with a mature table and mixed Turkish/English; birth-time content for a level-1 short campaign written entirely in Turkish (item 11.7) will differ in density. The hand-built bible-equivalent (≈230k tokens, 72 site entries of which 21 detailed, 86 dossiers, 13 factions with 3 full dossiers) sits between the standard and epic estimates, which is a sanity check on the per-unit units, not a validation of the totals.
- Dollar cost deliberately not given: model pricing should be looked up (claude-api skill), not quoted from memory; the split of calls by model (Opus generation + same-model critique per item 15, Haiku for formatting/index) is left for the model-routing decision in item 19.
- Files read in full: docs/campaign-designer-plan.md only. Everything else was measured (sizes, headings, table rows, a few sample rows/records); the original-repo NPC and encounter files and the SRD data were sized but not opened.

# Item 19 — Pipeline mechanics (reliability-first design)

## Q1. Who is the designer process?

**Recommendation: a thin main-session *conductor* that never writes bible prose and never reads `design/dm-only/`; each generation phase is one Workflow script (deterministic fan-out, journaled); every LLM write happens inside a fresh-context subagent; every registry/JSON write happens in a Python script called by the conductor.**

Rationale, per constraint:
- *Context size.* Ashen Crown's bible is ~60k Turkish words (`campaigns/ashen-crown/reference/*.md` + `npcs-full.md` + `world.md`, measured with `wc -w`) plus ~136 KB JSON — roughly 100k+ tokens, and epic is bigger. Generated in the main session (today's `/dm:dnd new`, `SKILL-commands.md` lines 9-54) it would sit in context, be compacted mid-phase, and half-written files would be the only record. Subagents start fresh (`workflow-authoring`: agents get a fresh context, return text or a schema-validated object), so the main session's context stays at "manifest + public summaries" regardless of scale.
- *Coherence.* The registry (item 3) is the shared memory, but it must be **single-writer**: subagents never open `entities.json`. They write one JSON fragment per entity to `design/_staging/<phase>/<entity_id>.json` (plus the prose file), and the conductor runs `design_registry.py merge --phase N`, which upserts by id, refuses stamped-field changes outside a phase rerun, writes to a temp file and `os.replace`s. This is needed because today's stores are not crash-safe: `factions.py._save` (line 97) and `goals.py._save` (line 73) overwrite in place.
- *Two-layer approval (item 4).* Secrets are generated inside subagents whose output **schema has no field that can carry secret text** (`{entity_ids[], public_summary, counts, warnings[], files_written[]}`); secret prose exists only on disk under `dm-only/`. The conductor shows the user `design/_approval/phase-N.md`, generated by `design_approval.py` from the registry's `public`/`discoverable` fields — never from agent returns. Critique agents read `dm-only/` from disk in their own context and return only a verdict. So the main session never holds a secret it could show.

Alternatives: (a) main session generates directly — simplest, fine for `short`, but not compaction-safe and it *must* know secrets to write them; rejected. (b) plain Agent-tool subagents without Workflow — no journal, no fan-out control, manual retries; acceptable fallback if the Workflow tool is unavailable, since the manifest (Q3) makes resume independent of the journal anyway.

## Q4. Checkpoint granularity and failure handling

- **Granularity = one entity (fan-out) or one phase (single-writer).** Each agent's contract is "write the prose file and the stage fragment, then return"; the file on disk is the checkpoint, not the return value.
- **Agent returns nothing** (`agent()` → `null` on skip or terminal error): the script logs it and continues; `reconcile` finds the missing fragment; the conductor reruns the phase workflow for the pending list, up to 2 attempts per entity, then marks it `failed`. A phase with failed entities can be shown but **cannot be approved**; the user sees "3 of 27 NPCs failed twice: ids …".
- **Validator errors**: `design_check.py` output is grouped by entity id; each errored entity gets a targeted fix agent (prompt = its file + the error lines + the rubric), ≤2 loops, then surfaced to the user "did not pass, because…" (item 15 semantics).
- **Rate limits / API errors**: the Workflow tool retries; if a whole run dies, `Workflow({scriptPath, resumeFromRunId})` replays the journal prefix; independent of that, the manifest work-list shrinks on every reconcile. Concurrency is a dial (`design.concurrency`, default 6, epic may raise to 10).
- **Compaction mid-phase**: the conductor holds nothing that matters. Procedure rule: after every workflow return the *first* action is `design_manifest.py update` and `git add design/ && git commit`, before any text to the user. `design_manifest.py` also writes `<runtime_dir>/active-design.json` (same pattern as `autosave_checkpoint.py`'s `active-campaign.json`) so a compacted or restarted session re-orients with `design status`.

## Q5. Approval loop UX

Per phase the user sees only `design/_approval/phase-N.md`: (1) counts vs the scale band (target / actual / ok); (2) the public name list with one-line public summaries and the entity ids; (3) for phase 3, the **player** SVG map; (4) on a rerun, a script diff against the previous approval file (added / removed / changed entities); (5) validator warnings and the critique record ("passed after 1 fix loop"); (6) any `failed` ids. Never any `secrecy: secret` field. A correction is free text; the conductor classifies it into item 14's scope (fact / entity / phase), runs `design_revise.py plan "<text>"` which lists affected entities and files via the wiki-link scan, shows that list, and on confirmation reruns only those entities (same workflow, args = affected list), then validator → critique → diff. # Item 19 — Pipeline mechanics (cost/throughput lens)

## Q1. Who is the designer process?

**Recommendation: the main session is orchestrator and approval desk only; it never generates bible content.** Per phase it (a) runs Phase 0 dice via `dice.py`, (b) launches one **Workflow** run (`.claude/skills/dnd/workflows/design-phase.js`, args = `{campaign, phase, entity_ids?}`), (c) reads only the script-generated public summary, (d) runs the approval loop, (e) records approval in `design.json`. Inside the workflow every writer is a fresh-context subagent that **writes files to disk itself** and returns a schema-validated object with *public fields only* (`entity_id, name, public_summary, counts, files_written, warnings`) — no `secret` field exists in any return schema. `design/dm-only/**` is therefore never in the main session's transcript, which is the only place the user reads. ## Q4. Checkpointing and failure

Granularity = **entity**: a writer's last action is `design_manifest.py mark <id> written`; critique marks `critiqued`; the validator marks `validated`. Nothing is "done" in memory only. # Item 19 — Pipeline mechanics (owner-player lens)

Governing rule, derived from items 4 and 11: **the main session is a blind orchestrator.** It holds dials, the manifest, public projections and validator verdicts; it never generates, reads or relays anything with `secrecy: secret`. Secrets are produced inside subagents that write files and return only schema-constrained public summaries. This is stronger than "the user does not open dm-only/": the secret text is never in the conversation at all, so a compaction summary, a careless recap or a later `save` cannot leak it.

## Q1. Who is the designer process

**Recommendation — three roles, fixed per phase:**

| Role | Who | Phases |
|---|---|---|
| Interactive owner loop | main session | P0 dials, every approval gate, corrections |
| Generation + critique + fix loop | one Workflow run per phase (`scripts/workflows/design_<phase>.js`) | P1-P8 |
| Deterministic steps | Python via Bash from the main session, `--redact` output | pre-rolls, merge, validate, seed, render |

Why Workflow and not the main session (today's `new`, `SKILL-commands.md`): (a) context — an epic bible is ≈ 215k tokens of final Turkish content (arithmetic in Q7), far beyond what one context can generate coherently; (b) secrecy — a main-session generator has the secret in its own output stream; (c) the ≤2 critique/fix loops of item 15 are a deterministic loop, exactly what the Workflow script encodes, and the intermediate fix lists (which name secrets) never surface. Why not one Workflow for all phases: approval is a real conversation with the owner and Workflow agents cannot talk to the user; the plan already asks for a gate after each phase. Between runs the shared memory is the disk: `design/entities.json` + `design.json` + the phase's fragments, not the journal. **Fallback ladder** when Workflow is unavailable (headless/plugin): the same units run through the Agent tool sequentially (slower, same secrecy); the main session never generates a secret-bearing phase itself.

What the main session holds in context during birth: `design.json` (public part), `design/.build/public-index.json` (a projection `registry.py export --public`: no entity with `secrecy: secret`, no secret fields), `design/index.md` public columns, redacted validator output, the workflow's returned public card.
